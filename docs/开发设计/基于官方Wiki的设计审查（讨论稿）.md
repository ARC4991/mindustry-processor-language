# 基于官方 Wiki 的设计审查（讨论稿）

> 状态：审查记录，不是已冻结的语言规范。本文将当前 MPL/MIL 设计与 Mindustry 官方 Logic Wiki 对照，列出已覆盖的约束、必须补齐的语义，以及需要用游戏原型验证的假设。

## 依据与边界

官方 Wiki 自称“官方但不完整”的 Logic 手册，因此它适合作为基础约束来源，而非全部指令和属性的最终清单。实现某个具体宏、单位属性或建筑控制方法前，仍应以目标 Mindustry 版本的源码/API 和游戏内编辑器参数表复核。

- [Logic 简介](https://mindustrygame.github.io/wiki/logic/0-introduction/)：列出单位/建筑控制、显示绘图、消息输出、内存、开关和数学等能力。
- [术语表](https://mindustrygame.github.io/wiki/logic/1-glossary/)：定义目标层的数值、对象、Unit、Building、内容类型和 senseable 属性。
- [变量与常量](https://mindustrygame.github.io/wiki/logic/3-variables/)：说明 `@counter`、`@unit`、`@links`、`@ipt`、`@time`、`@tick`、`@mapw`、`@maph` 的行为。

## 已被当前设计覆盖的约束

| Wiki 事实 | 当前设计回应 | 状态 |
| --- | --- | --- |
| 目标只有数值与对象；对象给数值参数时会隐式变成 0/1，数值给对象参数时会变成 null | MPL 禁止对象/数值、Bool/数值等隐式转换 | 已覆盖；需在 MIL 降级时保持此保护 |
| `@counter` 是下一条指令地址，可赋值跳转 | MIL 使用它实现结构化跳转与函数返回 | 已确认 |
| 同时只能绑定一个 `@unit`；保存的单位引用不能作为通用持久对象表 | for Unit 是临时绑定；`UnitSet.get(...)` 与编译器提升产生受预算约束的长期句柄，私有 runtime 以隐藏 flag 区分和恢复 | 已冻结；v146 哨兵遍历退出性仍需原型 |
| 处理器每 tick 执行 2 / 8 / 25 条指令 | 不引入语言级 `yield`，并计划做展开后的指令规模报告 | 已覆盖方向，执行语义仍需冻结 |
| `@links` 会随链接/解绑变化，`getlink` 返回 Building 对象 | `Building.getAll类型()` 限定处理器已链接建筑，而非全地图建筑 | 已覆盖方向，动态链接语义仍需补齐 |
| 目标数值底层为 64 位 double，位移按 64 位 long | MPL 使用 32 位饱和 `Int` 与有限 `Float`，位运算仅允许 `Int` | 已冻结；profile 必须插入规范化 lowering |

## 必须先决定的语义

### 1. `Int` 的精确范围与溢出

目标把普通数值存为 double；并非所有 64 位整数都能精确表示。MPL 不能只写“Int 映射为数值”而不定义保证范围。

已冻结为：`Int` 是范围 `-2_147_483_648..2_147_483_647` 的有符号 32 位整数，加减乘饱和、余数商向零截断、位操作规范为 32 位补码、移位量按 `& 31` 处理。这样内存地址、tag、数组长度和多处理器邮箱 ABI 都不会受到 double 精度或目标 long 宽度差异影响。`Float` 只表示有限 double，除零和非有限中间结果经总定义归一化，绝不把 NaN/Infinity/null 暴露为语言值；详见《MPL 语言规范（讨论稿）》4.4。

### 2. `null`、可空对象与动态世界状态

Wiki 明确存在 null：无效对象参数会变为 null，数值语境又会变为 0。MPL 已禁止这种隐式转换，但尚未定义下列场景的公开类型：

- 已链接建筑在执行期间被拆除或解绑；
- radar/ulocate/getlink 找不到目标；
- 包注入的硬件在地图部署时不满足声明；
- Unit 遍历候选在循环体期间死亡或被其他处理器改变状态。

建议引入仅用于对象引用的可空写法（例如 `BuildingRef?`、`UnitRef?`），并要求显式判空；或者第一版把这些 API 设计成只能在编译器可保证存在的范围内使用。不能用 `0`、`false` 或静默跳过替代语言级语义。

### 3. 执行边界、顶层初始化与持久状态

目标处理器会跨 tick 从下一条指令继续执行，`@ipt` 只表示每 tick 的执行额度。v146 源码进一步确认：程序计数器越过末尾后，会在下一次取指时被执行器重置为第 0 条。MPL 不应额外生成或宣传“隐式 main 循环”，而要忠实保留这一目标行为。仍需要回答：

- MPL 末尾将生成 `stop`，因此顶层初始化默认只执行一次；持续逻辑由显式 `while` 表达，不需要额外的隐式状态生命周期。
- 哪些变量、对象和字符串跨 tick 持久，何时构造/析构？
- 长循环在 tick 中断后，`break`、`return`、Message 自动 flush 和组合 Display flush 的可观察时机是什么？

建议先将“顶层就是顺序指令流、编译器不生成主循环”写入规范；再单独设计持久状态语法或受控对象生命周期。否则用户无法判断 `var damagedCount = 0` 是再次执行初始化还是因控制流未回到开头而长期累积，也无法估算 tick 间行为。

### 4. 链接是静态硬件契约还是动态集合

`.mplh` 的 `link("memory1")` 是部署时对游戏链接变量名的静态映射，但 Wiki 说明 `@links` 与 `getlink` 在游戏运行时可改变。需要冻结：

- 声明的链接在运行中被解绑时，非内存硬件对象的操作如何表现；
- `Building.getAll类型()` 每轮是否读取当前链接集合，是否允许同一轮新增/删除；
- 链接编号、内容类型和组合屏幕尺寸是在构建期、地图加载期还是每次执行时验证；
- 包通过 `with` 收到的 Display/Message 是否可声明独占、共享只读或共享可写。

建议把 `.mplh` 视为部署契约：构建期检查静态参数，加载/启动期做一次硬件匹配诊断；运行期动态解绑则返回显式可空状态或终止相关高层操作，不能伪装为编译期失败。

### 5. 传感、查找与内容类型 API

Wiki 区分 Building（世界中的对象）和 BuildingType/UnitType（内容类型），并把可感知属性列为 `senseable`。当前示例使用 `unit.health`、`Unit.getAllAlpha()`，但还缺少可维护的属性与内容模型：

- 哪些 `unit.xxx` / `building.xxx` 属性由目标版本生成，读写权限分别是什么；
- Item、Liquid、Block、UnitType 等内容值的 MPL 类型与命名规则；
- radar、uradar、ulocate、sensor 的高层 API；
- 未找到 radar/locate 结果的可空返回与排序/筛选语义。

建议编译器按 `target.mindustry` 配置加载一份版本化的内容/属性描述表，并由它生成 `Unit.getAllAlpha()`、类型检查和 IDE 补全；不要把属性名散落硬编码在编译器里。

### 6. Unit runtime 的可行性原型

Wiki 只保证 `@unit` 是单一当前绑定单位；v146 源码的 `UnitBindI` 已确认：对可逻辑控制的己方单位类型，`ubind` 使用每个类型的游标循环选择缓存中的下一单位，无候选时绑定 null。v146 也没有向 mlog 暴露单位实体 ID，因此编译器若需要跨代码重载恢复受控单位，只能以隐藏 flag 为基础；写 flag 同时认领 LogicAI。以下仍必须通过游戏原型验证后才能承诺：

- 空集合和遍历终止如何检测；
- 单位死亡、生成、被其他处理器重新绑定/控制时的行为；
- 嵌套单位遍历和函数调用后如何恢复外层绑定；
- 隐藏 tag 的编码、RTS AI 与手写 mlog 的冲突诊断，以及多个 LogicAI 的抢占恢复。

在原型结论出来前，第一版应禁止嵌套单位遍历与借用 Unit 跨函数传递。

### 7. 函数、递归与自动内存预算

内存已改为编译器统一管理，因此函数调用栈、递归、数组、String 拼接和 `new` 都必须具有静态上界。当前规范仍未决定：

- 是否允许递归；允许时如何给出最大深度；
- 函数调用是否可重入，参数/局部变量是否为每次调用独立槽位；
- 数组长度、动态数组增长与元组逃逸的容量证明规则；
- `new` 的释放语义和跨 tick 对象的最大并发存活数。

建议第一版：禁止递归、只接受编译期固定长度数组、要求 `new` 的并发上界可静态推导；后续再用显式容量或受控注解扩展。这样与“无运行时内存失败”一致。

### 8. I/O 的缓冲、上限与副作用顺序

Wiki 说明显示绘图、消息输出和开关输入是独立的目标能力。MPL 已有 `Message.print()` 自动 flush 与组合 Display，但还应确定：

- 一次 `Message.print()` 的多个参数与自动 flush 是否原子地发生在同一 tick；
- 字符串表分发、print 缓冲和游戏消息块自身限制的交互；
- 组合 Display 的跨屏裁剪、每块物理屏幕的命令顺序及 flush 次数；
- `Switch` 的读取 API、边沿检测是否由标准库提供，以及输入在 tick 中的取样时机。

这些规则应在 API 文档中用“可观察的命令顺序”描述，而不承诺实现细节。

## 仍缺少的标准库入口

为避免 MPL 源码直接出现 `@`，建议后续为 Wiki 中已有的处理器常量提供受限的高层入口：

| 目标常量 | 建议高层入口 | 需要决定 |
| --- | --- | --- |
| `@time` / `@tick` | `Clock.timeMs`、`Clock.time`、`Clock.tick` | 时间单位、精度与确定性 |
| `@mapw` / `@maph` | `Map.width` / `Map.height` | 是否作为编译期常量；通常应是运行期只读值 |
| `@ipt` | `Processor.instructionsPerTick` | 用于性能监控还是仅诊断 |
| `@this` / `@thisx` / `@thisy` | `Processor.self` / `Processor.position` | Processor 对象的可见属性 |
| `@links` / `getlink` | `Links` 或受限的 `Building` 查询 API | 动态集合、可空与遍历稳定性 |

这些名称是建议，尚未成为语法承诺。

6. 再实现 MPL → MIL 的最小闭环和源映射。
