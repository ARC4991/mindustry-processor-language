# 多处理器协作、分片与共享内存（讨论稿）

> 状态：已确认采用“单处理器优先、需要时编译为多处理器部署包”的方向。本文冻结 v146 基线的边界：每个输出处理器都必须独立满足 mlog 上限；多个处理器通过声明的共享物理 Memory 协作，而不共享处理器变量。任意业务代码的自动并行化仍须经效果分析验证，不能仅因超过 1000 条指令就静默改变顺序语义。

## 目标与核心规则

Mindustry 对**每个**逻辑处理器最多接受 1000 条 mlog 指令，而不是对整张地图或一个 MPL 项目设总上限。因此 MPL 可以把一个项目编译为一个处理器部署包：一个协调处理器和零个或多个工作处理器，各自产出独立 mlog。

规则如下：

1. 当优化后的完整程序在一个处理器内满足 profile 限制时，仍只输出一个 `Main.mlog`；不会为小程序引入通信、延迟或额外硬件。
2. 多处理器模式是**部署模型**，不是游戏自动创建整套地图硬件的能力。`.mplh` 必须先声明处理器拓扑、每个处理器的本地链接和共享物理内存；编译器输出待粘贴的多份 mlog、部署清单，以及可选的运行时蓝图。
3. 每个 shard（分片）都有独立的 `@counter`、`@unit`、mlog 变量、函数 ABI、文本/绘图缓冲和虚拟槽位。虚拟内存绝不跨处理器共享。
4. 只有真实的 Memory Cell/Bank 数值槽可跨处理器通信；它不能传递 Unit、Building、Display、Message 或任意处理器对象引用。v146 没有读取/写入另一个处理器变量的跨处理器能力。
5. 一个 shard 的最终产物必须独立满足 target profile 的 1000 指令、500 标签、16 token/行及 I/O 缓冲限制。构建报告同时显示每片与总计，但“总指令数大于 1000”本身不再是错误。

这让总计算预算可以随处理器数量扩大，但不会让任一处理器突破游戏限制，也不会把多个处理器伪装成一个原子 CPU。

## 产物与部署

多处理器构建输出目录暂定为：

~~~text
build/v146/
  Main.mlog
  Worker-0.mlog
  Worker-1.mlog
  runtime.msch             # 可选；仅处理器和 Memory
  deployment.json
  report.json
  source-map/...
~~~

`deployment.json` 的正式字段由《[Profile 与构建产物 Schema（讨论稿）](数据格式/Profile与构建产物Schema（讨论稿）.md)》定义，至少记录：

- shard 名称、处理器种类、每片的指令/标签/虚拟槽位用量；
- 每个本地 mlog link alias 应对应的游戏建筑类型；
- 共享 Memory 的逻辑名称、容量、每个 shard 的本地 alias 与读写角色；
- 物理内存布局指纹、通信 ABI 版本、私有 Unit runtime 的所有者 shard；
- I/O（Message、Display、可写建筑）的唯一写入者。

### 运行时蓝图边界（已确认）

若构建生成 Mindustry 蓝图（暂定文件名 `runtime.msch`），蓝图**只包含逻辑处理器和编译器管理的 Memory Cell/Bank**。它可以表达处理器拓扑、共享 Memory 的相对位置以及处理器到这些 Memory 的内部连接；它不包含、也不尝试放置 Display、Message、Switch、炮塔、单位工厂或任何业务建筑。

换言之，蓝图解决的是“让多份 mlog 有可部署的计算与共享存储骨架”，而不是替玩家复制整张地图。`runtime.msch` 不替代各 shard 的 `.mlog`，也不能把外部硬件绑定固化为可移植布局。

安装者先放置或导入这份蓝图，再把对应 `.mlog` 写入每个处理器；Display、Message 和其它业务建筑仍由玩家按地图需求自行放置、连接。`deployment.json` 将所有非 Memory 链接列为**外部硬件契约**，只说明拥有者 shard、期望的 alias、类型、读写权限和组合屏布局，绝不把这些建筑写入蓝图。未来 `mpl hardware check` 根据该清单检查各处理器的范围、队伍、类型和必要链接；它不能替游戏自动布线。不同处理器的 alias 是否最终指向同一个 Bank 不能依赖未暴露的实体 ID 判断，必须由启动握手在同一数值地址空间中互相确认。

如果部署包要求工作处理器，协调处理器只在完成启动握手后开始对外 I/O。缺失的 shard、失效 Memory 链接或布局指纹不一致属于部署失败：运行时保持安全等待状态，不能假装完整程序仍在正常运行。

这里的“等待”不能直接生成 `stop`。v146 的 `stop` 会让该处理器的 `@counter` 永远停在自身，新的共享 Memory 消息不会自动唤醒它。因此所有长期 Worker 都由编译器生成一个极小的邮箱轮询循环；一次性顶层程序则由 `Main` 在收到全部结果后发送 shutdown，再让 Worker 和 `Main` 各自执行 `stop`。这只是部署 runtime 的内部调度循环，不改变 MPL 顶层代码“默认执行一次”的表面语义。

## 编译器自动拓扑

`.mplh` 不声明处理器、物理 Memory 或虚拟槽。单处理器闭环生成隐式 `Main` shard；多处理器阶段由编译器在指令数超限或明确的性能目标下选择 shard 数量、处理器类型、函数/数据分区和共享 Memory。`mpl.json` 的 `runtime.processors` 与 `runtime.memory` 只给出每种块的数量上限，不指定坐标、alias 或手工拓扑。

编译器为每个共享段生成逻辑 ID，并在 `deployment.json` 中列出每个 shard 的本地 alias、读写权限和单写者归属。这些名称不会成为 MPL/MIL 中可读写的 Memory 值。同一物理 Memory 只有在所有参与 shard 的 alias 最终指向同一个游戏 Cell/Bank 时才是共享段；否则启动握手不会完成。每个处理器还必须满足连接范围、同队和权限约束。v146 的 Micro / Logic / Hyper 默认链接半径分别是 10 / 22 / 42 格；一个 Bank 仍只有 512 个槽，多处理器链接同一 Bank 不会增加容量。

非内存硬件固定归 `Main` 所有，且永远属于蓝图外的地图契约。用户只把 Message、Display、Switch、炮塔等业务建筑手动连接到蓝图最左侧的 `Main`；Worker 不接受手动外部链接。一个 Display、Message 或可写建筑若要被 Worker 使用，必须通过共享 Memory 协议把数值请求交给 `Main` 执行，不能跨处理器传递 Building 对象。处理器的确定性坐标、代码头标识、连接说明和 alias 核验见《[蓝图处理器识别与手动连接（讨论稿）](蓝图处理器识别与手动连接（讨论稿）.md)》。

## 分片边界与可观察语义

不能把任意超过 1000 条指令的顺序程序按行切成两份：函数调用、局部变量、`@counter` 跳转、Unit 借用和硬件写入都会改变含义。故分片器采用以下边界：

- `Main` 保留顶层顺序控制流、同步函数调用、所有对外 I/O，以及默认的 Unit runtime 所有权。
- 先自动抽离编译器内部且已证明无外部副作用的 runtime 服务，例如纯数值批处理、字符串/对象池的内部维护步骤；这些服务使用固定通信 ABI。
- 用户业务代码只有在后续的效果/所有权分析证明独立，或在未来显式并发语法中声明任务边界后，才可移动至 Worker。跨 shard 调用不是普通函数调用，而是异步消息。
- 若单个不可分割的顺序区域在优化后仍超过 1000 条，构建失败并报告该区域、内联/运行时成本和可分片候选；编译器不能为“能编译”而改变源码的顺序与原子边界。

因此多处理器首先用于扩展可独立调度的工作和编译器 runtime；它不是无条件的“把任何 MPL 程序自动并行化”承诺。

跨 shard 消息在任意两个 mlog 指令之间都可能被观察到，且实际到达可晚于一个 tick。每个处理器在一次 Building 更新中会连续执行自己的 IPT 批次，并可能积累到最多约 `5 × IPT`；不同 Building 的更新顺序不是 MPL 语义。MPL 不把它描述为同步共享变量，也不承诺同 tick 可见。当前没有向用户公开 `await` 或线程语法；这些异步性只存在于编译器生成的 runtime。将来开放用户任务时，必须单独定义可空结果、取消、超时和跨 tick 顺序。

## 共享 Memory 协议

共享段按照“单写者、明确所有权”布局，而不是提供可随意读写的全局堆：

~~~text
布局头（magic、ABI 版本、布局指纹、部署 epoch、ready 位、每 Worker heartbeat）
  + Main → Worker[i] 的单生产者/单消费者邮箱
  + Worker[i] → Main 的单生产者/单消费者邮箱
  + 每个 shard 独占的物理数据区
  + 仅由 Main 管理的共享池元数据（若需要）
~~~

布局器能在不移动现有 Array、String 和对象池分配的前提下追加该 header：优先复用已有 Memory 的剩余容量，容量不足时再在 `runtime.memory` 数量限制内增加 Bank/Cell。header 固定占 `5 + Worker 数量` 个槽。代码生成器已按 allocation 的 slice 发射跨段安全的握手读写，且最终 mlog 生成后才逐 shard 统计指令、标签和 token。

固定宽度 SPSC 邮箱的物理 ABI 和结构化指令发射也已实现。每个邮箱占 `3 + payloadSlots` 个槽，顺序为 `version`、`acknowledgedVersion`、`kind`、payload；生产者和消费者在规划期固定且不能互换。它目前是编译器 Runtime 的内部构件，尚未接入自动 helper 分片、长期轮询调度和用户语法。

启动采用双阶段确认，避免 Worker 在重新部署时误用旧的 `ready=1`：

1. `Main` 写 `ready=0`、magic、ABI、布局指纹和 epoch，并清空 Worker 槽；
2. Worker 在每次 `read` 前把目标变量重置为 `null`，验证 header 与 `ready=0` 后写入负 epoch；等待期间若仍看到 `0`，会重复该回执；
3. `Main` 收齐负 epoch 后初始化 String、对象池等共享存储，再写 `ready=1`；
4. Worker 再次验证全部字段，写入正 epoch 后才进入自己的用户/runtime 代码；
5. `Main` 收齐正 epoch 后才检查外部硬件并进入顶层程序。

每个邮箱记录固定数量、固定宽度的数值字段。生产者按如下版本协议发布一条记录：

1. 等待 `version == acknowledgedVersion`，证明单槽邮箱中没有未消费消息；
2. 写入奇数 `version`，表示记录正在写入；
3. 写入 `kind` 和全部 payload 数值；
4. 最后写入相邻的偶数 `version`，表示提交；版本达到 `2,000,000,000` 后只在空邮箱状态安全回绕到 `2`；
5. 消费者读取 `version`、kind/payload、再次读取 `version`；仅当两次相同、非零且为偶数时接受；
6. 消费者写 `acknowledgedVersion` 并读回确认，生产者之后才能发布下一条消息。

单条 mlog `read` / `write` 是目标层可切开的最小操作，不能假定多槽 payload 原子。上述协议使生产者在跨 tick 暂停时，消费者只会看到“未提交”，而不会把半条消息当成有效数据。每个地址只能有一个静态写入者：payload 归生产者、确认/消费游标归消费者、布局头和全局分配器归 `Main`。没有 CAS 的 mlog 上不实现多写者竞争队列或并发自由链表。

v146 中多个 Building 的更新顺序不是 MPL 的调度保证；每个处理器会执行自己的 IPT 指令批次，写入何时被另一个处理器在同一 tick 看到不能作为语言语义。邮箱必须按“本 tick 或后续 tick 才可见”设计。另一个目标层陷阱是：对无效或错误类型的 Memory 链接执行 `read` 时，输出变量可能保持旧值，而非可靠地得到 `0`。启动握手在每次读取前先写入本地哨兵值，并同时验证 magic、ABI 版本、布局指纹和 epoch；任一字段未改变或不匹配都视为尚未连接，绝不把旧值当作有效共享数据。当前 Worker 槽承担启动阶段的双相回执；持续心跳、掉电检测和安全停机要与后续邮箱调度循环一起实现，不能把一次启动回执伪装成长期存活证明。

通信字段只能是严格定义的数值、Bool、Int 编码值或物理池句柄。对象引用、`@unit`、硬件对象和本地虚拟槽位不能跨 shard 发送。版本号、epoch、句柄和计数器必须落在 MPL 最终冻结的精确 `Int` 范围内；在此之前，不把位级编码写死为表面语言保证。

## 内存分配、回收与优化

多处理器不应以复制 runtime 为代价换取更多指令空间。链接器先进行全项目优化和资源规划，再决定分片：

1. 常量传播/折叠、条件简化、死代码删除、复制传播、公共子表达式消除和无副作用函数的受成本约束内联；
2. 基于活跃区间和干涉图的虚拟槽位复用。该复用只在**同一 shard**内发生，绝不把两个处理器的变量当成同一地址；
3. 字符输出表、运行时 helper 和只读常量在部署包内去重；I/O 服务只保留一个所有者；
4. 物理 Memory 按所有者划分区间。对象池/字符串块使用静态证明的最大容量、类型化空闲表和生命周期结束后的复用；字段在重新分配前由所有者初始化；
5. 跨 shard 的可变对象只有在消息协议规定了所有权转移后才能移动。第一版不提供通用并发分配器或隐式垃圾回收；共享池的分配、释放和代际校验由 `Main` 串行管理。

构建报告必须区分：每 shard 的虚拟槽、共享通信头/邮箱、私有物理区、对象池、字符串 runtime、布局元数据和可回收峰值。优化器的成本模型同时考虑指令数、标签数、IPT、共享 Memory 槽、消息读写开销、链接数量和处理器数量；只有总成本降低且每片满足限制时才接受分片方案。

## Unit、I/O 与所有权

UnitRef 缓存、隐藏 flag tag 与扫描游标属于编译器私有 Unit runtime：它们的引用槽属于一个 shard，不能放进共享 Memory，也不能转移给另一个 shard。每个 Unit runtime 在部署清单中固定归属**一个** shard；owner 执行绑定、tag 验证与 `ucontrol`。Worker 不得直接对同一组单位执行 `ucontrol`、`uradar` 或 `ulocate`，否则会抢占 LogicAI。第一版不开放 Worker 的单位动作请求；未来若开放，只能由 owner 验证 tag、存活和 controller 后执行数值化命令。

同样地，Message、Display、建筑写入和 print/draw 缓冲均由一个 shard 独占。多处理器方案提高吞吐量，但不放宽“同一可写游戏对象只能有一个 MPL 写入者”的部署规则。

## 编译管线与后续实现

在 HIR 优化之后新增 `ShardPlan`：

~~~text
HIR
  → 全项目优化与效果/所有权分析
  → ShardPlan（角色、边界、通信、资源）
  → 每 shard 的虚拟/物理布局
  → 多份 MIL / mlog
  → 每份目标限制校验
  → 部署清单、报告、源映射
~~~

当前已经实现 `ShardPlan` / `RuntimeTopologyPlan`、逐 shard 最终 mlog 目标限制校验、多处理器紧密布局、独立 MIL/mlog 构建产物、所有处理器到同一组 Runtime Memory 的蓝图内真实连接，以及带哨兵读取和双相 epoch 回执的启动握手。普通编译流程仍只生成一个隐式 `Main`；编译器尚不会把用户程序自动切成 Worker。下一阶段依次实现：

1. 把现有 SPSC emitter 接入编译器内部 helper 的安全抽离，并生成长期轮询、持续心跳和 shutdown runtime；
2. 经效果分析验证的用户任务分片，以及未来的显式并发语法；
3. 完善多 shard 硬件检查和运行时部署诊断。

在步骤 3 完成前，普通 MPL 项目超过 1000 条指令仍是单处理器构建错误；当前多 shard API 只服务于已明确分离的编译器 Runtime 原型，不能只把顺序代码硬切后输出看似可部署的蓝图。

## v159.7 的可选优化

v159.7 可以在链接到另一个 LogicBuild 后按变量名读取/写入其变量。这不是 v146 的能力，且远端变量会随代码重载改变，也没有原子读改写保证。因此 MPL 的跨版本通信 ABI 仍以共享物理 Memory 为准；将来 v159.7 profile 可以在效果、所有权和部署条件都满足时把少量邮箱访问降级为远端变量访问，但不能改变 HIR 语义或让包依赖它。
