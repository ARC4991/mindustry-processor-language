# 语言设计完备性审查（讨论稿）

> 状态：v146 首个可运行闭环前的设计审查。本次修订已把会改变可观察行为的 P0 语义写入规范；余下工作以 profile 数据、ANTLR 文法、运行时原型和测试验收为主。

## 结论

MPL 的总体方向已经清晰：严格类型、高层 MPL 与受限宏的 MIL 分层、`.mplh` 硬件声明、编译器统一内存管理、无隐式主循环、v146 基线与 v159.7 可选优化。这足以继续实现基础控制流与函数。

设计仍不能宣称为 1.0：数组、泛型、用户并发和跨重新部署持久化被明确留到后续版本。不过数值、错误、String、对象、包、MIL、Building、I/O 与部署边界已有可实现规则；下列 P0 现在主要是实现和验收项，不再要求重新发明语义。

## 已明确且可作为实现输入的规则

- MPL 源码不能使用 `@`；MIL 才能使用受 profile 限制的基础宏。
- `.mplh` 只允许硬件与资源声明；MPL/MIL 不能直接访问 Memory。
- `Int`、`Float`、`Bool`、`String` 严格区分；仅允许 `Int → Float` 隐式提升，`Int / Int` 得到 `Float`。
- 顶层 `main.mpl` 按指令顺序执行，不生成虚假的 `while(true)`。
- 函数第一版使用静态、不可重入 ABI；禁止直接/间接递归。
- UnitSet / BuildingSet 使用编译器 runtime；用户看不到或读写 flag。UnitRef 缓存、隐藏 flag tag、扫描游标和恢复元数据均为内部实现；公开 Unit API 为 `getAll类型()`、`.where(...)`、`.take(n)`、`size`、`get(...)` 和对象操作。
- `Message.print(...)` 自动 flush；`.mplh` 通过 `link("message1")` 显式绑定游戏 mlog 链接变量。
- 每次构建选择精确 target profile；v146 是基线，v159.7 只能做等价优化。
- 单处理器是默认且无额外开销的部署；项目可声明多处理器拓扑。每个 shard 独立受 1000 指令等 profile 限制，虚拟槽彼此隔离，只能经共享物理 Memory 的单写者消息协议协作。
- 可选运行时蓝图只包含处理器和 Memory Cell/Bank；Display、Message 与其它业务建筑属于玩家自行连接的蓝图外硬件契约。
- `Int` 为有符号 32 位饱和整数；`Float` 为不会泄漏 NaN/Infinity 的有限 double；除零、移位、位运算和显式转换都有总定义。
- `new` 有显式构造但无 `delete`：编译器依据逃逸和活跃区间分配、回收固定上界对象池；无法证明上界即为构建错误。

## P0：控制流、状态与数值语义

1. **作用域和生命周期**：已冻结为“声明必须初始化、同域禁止重名、函数读取顶层变量须通过确定初始化分析、顶层末尾 `stop`”。需补正反例测试。
2. **跨 tick 预算**：长循环、Unit 遍历、String 输出被 IPT 切断时的可观察状态已定义；仍需把私有续执行状态、I/O 非原子边界和 IPT 报告落实为测试。
3. **数值和 Bool lowering**：已冻结 Int/Float 总定义与短路要求；profile 必须生成保护代码并建立 v146 golden test，不能让目标层 null 进入 MPL。
4. **错误模型**：已区分构建错误、部署期契约失败、可空查询和游戏世界的 best-effort 无效果；需为 `hardware check` 和诊断码实现对应验证。

## P0：硬件绑定与 I/O

- 硬件通过游戏提供的 mlog 链接 alias 映射，`.mplh` 不使用链接序号；alias 是比顺序下标更稳定的正式绑定方式，但重连后仍须作为部署期契约核验。仍需硬件检查命令验证名称、目标类型、链接是否存在及可写硬件冲突。
- `.mplh`、包注入和可写 shard 所有权已明确；仍需把 link 类型、重复硬件、失效链接和冲突翻译为稳定诊断。
- 多处理器 `.mplh`、共享 Memory 同一性、启动握手和 I/O 所有者已有设计；蓝图只包含处理器与 Memory，不能替玩家布置业务建筑。尚待实现部署清单 schema 与硬件检查。
- Display 的 Color、坐标、清屏/填充/描边状态、组合屏裁剪和 runtime 自动刷新预算已冻结；MPL 不暴露 `flush()`，仅生成的 MIL/目标代码可含刷新节点。Message 使用 UTF-16 代码单元、400 上限与自动 flush。需以游戏内测试确认 profile 成本。
- 需为 v146 的 Read/Write/Control/Radar/Sensor/Unit Control 等指令建立机器可读签名，而非只在文档中列出名称。

## P0：函数、对象和内存

- `new` 的构造、固定字段布局、对象身份、可空性、自动回收和容量证明已冻结；用户对象引用字段、析构与跨部署持久化明确后置。
- 静态 ABI 的实参左到右求值、Void 返回和顶层确定初始化规则已明确；仍需落实临时变量预算和函数调用图诊断。
- 构建报告必须分别计量物理槽、虚拟槽、对象池、String 序列、函数 ABI 与 runtime 元数据；它们可以汇总展示，但不能互相替代。
- 动态数组、可变数组和泛型容器不进入第一版；元组只保留为固定大小、编译期已知的后续功能。

## P1：模块、MIL 和版本化

- 包的单版本解析、锁定、循环拒绝、最低 target 与包 `.mplh` 资源汇总已冻结；registry 配置和 re-export 仍待 CLI/模块实现。
- `export`、public/private 与无继承对象模型已冻结；跨包名称重名按模块限定名诊断，第一版不提供隐式 re-export。
- MIL 已有公开宏目录和卫生边界；独立 grammar、用户 MIL 前端、source map 与 profile 禁止宏诊断仍待实现。
- profile 数据需要包含指令、内容、LAccess、权限、IPT、I/O 容量和地图规则前提；v159.7 每一项优化要有与 v146 等价的测试。

## P1：Unit / Building runtime

- 遍历终止条件、生成/销毁单位期间的行为、过滤 lambda 的捕获和求值次数、嵌套遍历限制、break/continue lowering 都需写成算法。
- UnitSet 的公开弱一致语义、禁止所有 Unit 嵌套、私有 flag/tag 运行时和多处理器所有权已形成独立契约；仍须以 v146 游戏内原型验证哨兵遍历在死亡/缓存变化下必定退出。
- 多处理器的 ShardPlan、共享 Memory 邮箱 ABI、版本/epoch 精确 Int 编码、任务效果分析和跨 shard 所有权转移必须在实现前完成原型；不能依赖游戏 Building 更新顺序实现锁或多写者分配器。
- Building 已冻结为 `.mplh` 已声明链接集合的 `LinkedBuildingSet`；保存、过滤、计数、索引、遍历、可空句柄、字段和控制 lowering 已实现，仍需完整 profile 生成、跨重连恢复与游戏内验证。

## P2：开发者体验与发布契约

- 诊断编号表、错误恢复、来源区间、mlog 源映射、格式化器和 JSON 构建报告。
- 项目配置 schema、`init` 模板版本、`check`/`build`/硬件检查命令、输出覆盖策略。
- 标准库版本、弃用策略、兼容性保证、示例与游戏内 golden test 的版本矩阵。

## 建议的冻结顺序

1. 完成 P0 的控制流、Int、硬件部署校验与 Message 细则；
2. 实现 if/while/for 与函数，使用 v146 golden mlog 测试验证 ABI；
3. 冻结对象/内存布局后再实现 `new`、数组和 String runtime；
4. 实现 `.mplh` 拓扑、每片预算与部署清单后，再引入共享 Memory runtime 和受证明的多处理器分片；
5. 最后引入包、MIL 用户入口、Unit/Building runtime 与 v159.7 优化。

在每一项进入实现前，应把对应章节从“讨论稿”改为“已确认”，并补充可执行的正向、反向与 profile 测试。
