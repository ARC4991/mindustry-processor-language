# 蓝图处理器识别与手动连接（讨论稿）

> 状态：多 shard 的紧密蓝图布局、逐处理器代码配置、Runtime Memory 自动连接与范围校验、双阶段共享 Memory 启动握手、部署清单坐标、中文连接说明、单 Main 外部硬件启动门、SPSC 邮箱、Worker 生命周期和纯数值 helper 自动分片已实现。

## 已确认规则

运行时蓝图仍只包含处理器和编译器管理的 Memory。Message、Display、Switch、炮塔等业务建筑由玩家在地图中放置并手动连接，不增加 I/O 适配器处理器。

所有外部硬件只连接 `Main`。即使后续构建产生 `Worker-0`、`Worker-1`，Worker 也不直接拥有手动业务链接；需要的数值输入和控制请求通过编译器管理的共享 Memory 协议与 `Main` 交换。这样每个项目只有一个外部 alias 命名空间，用户不需要判断某个 Message 应连接哪个 Worker。

蓝图中的处理器和 Runtime Memory 采用确定性紧密排列。布局器按 Micro/Logic/Hyper Processor 的 `1×1` / `2×2` / `3×3` 与 Memory Cell/Bank 的 `1×1` / `2×2` 真实占地检查重叠，在所有候选宽度中优先选择最小外接矩形面积，面积相同时再选择最短的最大边。方块之间不保留装饰性空白。`Main` 从左上角开始放置，随后按拓扑顺序放置 Worker。

`deployment.json` 为每个 shard 和 Memory 保存 `blueprintPosition`；Memory binding 的 `autoConnected: true` 表示蓝图已把该段写入对应 shard 的处理器配置。每个处理器都会连接同一组编译器管理的 Runtime Memory，不能只在部署清单中声明连接而遗漏 `.msch` 内的真实链接。构建目录还生成中文 `连接说明.txt`，按 `Main` 列出 MPL 逻辑名、类型和期望游戏 alias。

内部 Memory alias 必须以游戏对应的基础名开头：Memory Cell 使用 `cell__mpl_memN`，Memory Bank 使用 `bank__mpl_memN`。v146 读入处理器配置时会重命名不以 `cell` / `bank` 开头的链接；该命名规则保证蓝图导入后 mlog 引用与处理器的实际链接名仍一致。这些 alias 属于编译器私有命名空间，不暴露给 MPL 源码。

`.msch` 中每个方块的位置必须严格采用官方 `Point2.pack(x, y)` 格式：`x` 写入高 16 位，`y` 写入低 16 位。每个处理器的压缩配置都必须分别写入完整链接表，其中坐标是 Memory 相对当前处理器的 `short x, short y`，不能复用 `Main` 的相对坐标。两者位序或坐标基准错误都会造成“配置中存在链接、游戏中目标却不在该坐标”的静默断链，因此回归测试必须同时验证方块绝对坐标和每个处理器的链接相对坐标；发布前还要用 v146 官方 Runtime 放置蓝图，确认每个 Runtime Memory 链接均为 active、valid。

布局写出前还按 target profile 校验每个处理器到每段 Memory 的真实世界坐标距离；v146/v159.7 的 Micro、Logic、Hyper 半径分别来自 profile 的 10、22、42 格。任何链接超出半径都使构建失败，不能只因为压缩配置能容纳该相对坐标就把无效蓝图交给用户。

每份部署用 mlog 的第一行包含不计入指令数的识别注释：

~~~mlog
# MPL shard: Main / build: 12位构建哈希
~~~

Mindustry 没有给蓝图内单个处理器提供可持久显示的自定义方块名称，因此 MPL 不能直接在方块表面标出 `Main`。玩家先按“最左侧”识别；如果不能仅凭位置确认，就打开代码核对 shard 与构建哈希。哈希必须和蓝图名、部署清单及连接说明一致，不能混用两次构建的处理器或 mlog。

## 绑定名称的事实边界

`.mplh` 中的 `AlertBoard` 是稳定的 MPL 逻辑名；`link("message1")` 中的 `message1` 是 `Main` 处理器期望获得的游戏 alias。它不是 MPL 变量，也不是建筑实体 ID。

自由手动连接的实际 alias 只能由游戏在连接时分配，编译器无法在构建时读取未来地图状态。v146 的 `LogicBuild.findLinkName` 按建筑类型基础名选择最小空闲正整数；失效、换型或重连会重新计算名称。`getlink` 数字下标更弱：它只索引当前有效链接数组，任一链接失效都会使后续下标前移。因此 MPL 和 `.mplh` 不暴露链接数字。

用户连接 `Main` 后进入其配置模式，游戏会在有效链接建筑上绘制实际 alias。用户按 `连接说明.txt` 核对 `message1`、`display1` 等名称；多个同类建筑按数字从小到大连接。若实际名称不一致，必须先修正连接，不能让编译器把错误建筑当成逻辑常量。

编译器内部可以记录 `LinkSlotId` 和 `getlink` 下标，用于未来的启动检查与优化，但它们都不是语言 API。只有在全部预期链接有效、没有额外未声明链接且类型顺序已验证后，数字下标才可作为本次部署的内部事实。

## 启动时序

蓝图放置后处理器会立刻开始执行，而玩家此时通常还没有完成手动连接。编译器在最终 mlog 的 MPL 顶层语句前生成私有的链接就绪门：逐项用 `sensor alias @type` 确认每个 `.mplh` 声明的 alias 存在且方块类型正确。任一项未就绪时跳回同一个等待标签；全部就绪后才进入用户代码。

启动门只存在于最终 mlog，不出现在 MPL 或生成的 MIL 中。release 构建使用 `_0` 这类短标签，debug 构建使用 `mpl_hardware_wait_0` 这类可读标签；临时值使用编译器保留的 `__mpl_hwN`，不进入用户命名空间。全部就绪后顶层程序仍只执行一次，结束仍为 `stop`，启动门不表示 main 循环。

当前检查能证明已声明 alias 的存在和类型，不能证明没有额外链接，也不能恢复游戏重新分配过的 alias。连接错误时程序会保持在启动门；玩家应选中最左侧的 `Main` 进入配置模式，按 `连接说明.txt` 核对游戏显示的实际 alias。多 shard 构建还会先完成共享 Memory 握手，只有全部 Worker 确认同一个 magic、ABI、布局指纹与部署 epoch 后，`Main` 才进入外部硬件启动门。

## v146 与 v159.7

两个版本都把普通逻辑处理器链接保存为相对坐标与 alias，并在配置模式显示有效链接名称。v146 在失效链接恢复时会主动重新分配名称；v159.7 对同一方块类型的已有名称保留得更积极，但仍不能把 alias 当作永久实体 ID。MPL 的基线规则以 v146 的较弱保证为准，v159.7 只能做不改变语义的部署优化。
