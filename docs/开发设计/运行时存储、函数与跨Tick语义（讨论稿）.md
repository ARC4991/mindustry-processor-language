# 运行时存储、函数与跨 Tick 语义（讨论稿）

> 状态：以 Mindustry v146 源码为基线的实现约束。本文把已经能够由源码确认的事实与建议冻结的高层契约分开；未完成的对象池和动态 String 仍不属于当前编译器已实现的功能。

## 为什么需要这一层设计

MPL 不是在一台独立虚拟机上原子执行的程序。它会被展开为 mlog 指令，处理器每 tick 只执行有限条指令，且 v146 最多只接受 1000 条指令。因此，下列三个概念必须明确区分：

1. **处理器变量槽位**：mlog 中有名称的变量，可保存数值或对象引用；
2. **物理内存槽位**：Memory Cell/Bank 中可按运行时下标读写的数值槽；
3. **MPL 源语句**：可能展开为多条 mlog 指令，绝不是目标层原子操作。

把它们混为“无限虚拟内存”会使 `new`、数组、String 拼接和跨 tick 控制流产生无法兑现的承诺。

## 已确认的目标执行事实

v146 的 `LExecutor.runOnce()` 先取当前 `@counter` 所指指令、将计数器加一，再执行该指令。处理器每 tick 按 IPT 多次调用它；Micro、Logic、Hyper 的默认 IPT 分别是 2、8、25。

- 程序计数器越界时，下一次取指会回到第 0 条；MPL 在每个产物末尾追加 `stop`，因此顶层程序默认只执行一次。
- `set @counter address` 在当前指令结束后，下一次取指会从 `address` 开始。这是结构化跳转、函数调用和返回的后端基础，不会出现在 MPL 源码中。
- 一条 mlog 指令是唯一的原子单位。IPT 可在任意两条指令之间耗尽；变量、`@counter`、文本缓冲、图形缓冲和 runtime 私有槽会保留到下一 tick。
- 重新装载处理器代码时，`LExecutor.load()` 会重新创建处理器变量。处理器变量不是跨部署持久化存储；真实 Memory Block 的内容则不应被当作自动清零。

## MPL 的执行与求值契约

建议第一版冻结如下规则：

- 顶层可执行语句按源码顺序运行；函数声明本身不执行；末尾隐式追加 `stop`。
- 表达式、函数实参和 `Message.print` 参数从左到右求值。
- `&&`、`||` 是短路运算：右侧只在必要时求值；条件表达式只求值被选中的分支。它们不得直接降级为 mlog 的 eager `and` / `or`。
- 对一个普通变量的赋值，编译器先在私有临时槽中完成右侧计算，最后一条 `set` 才写入该用户变量。这样即使在中间跨 tick，外部代码不会看到半个数值结果。
- 硬件 I/O 不具备同样的原子性。一条 `Message.print(a, b)` 可能先写入部分文本、在下一个 tick 继续，并在最后才 flush；`Display` 的多条绘制命令也可能分多个 tick 填充缓冲。其他处理器仍可在这段时间写同一硬件。
- 第一版不公开 `wait`。目标 `wait` 会让自身反复执行并暂停后续指令；待将其设计为有明确暂停语义的 `Clock.wait(...)` 语句后，才可暴露给 MPL。MIL 的相关宏也必须标记为可暂停。

这不是新增“主循环”或 `state` 机制。循环被 IPT 切开后会自然从当前 `@counter` 恢复；开发者只需显式写 `while` 表达持续逻辑。

## 静态函数 ABI

第一版函数采用静态、不可重入 ABI。它利用 `@counter` 直接实现返回，不需要旧版 demo 中额外的“返回扫描”流程：

~~~text
调用点：
  计算实参（从左到右，结果先放调用点临时槽）
  set __fn_arg0 <实参0>
  set __fn_arg1 <实参1>
  op add __fn_return @counter 1
  set @counter <fn入口地址>

函数 return value：
  set __fn_result <value>
  set @counter __fn_return
~~~

执行 `op add` 时，v146 已经把 `@counter` 预增到下一条 `set @counter`；再加一得到跳转指令之后的真实返回地址。函数入口 label 在最终地址解析时换算为可执行指令地址，label 本身不占地址，也不计入 1000 条指令额度。

- 每个函数拥有独立的参数、局部变量、返回值和返回地址槽；`Void` 函数没有结果槽。
- 内部槽按函数序号、槽类别和参数序号生成，不直接拼接多个用户标识符，避免不同合法名称映射到同一个 mlog 变量。
- 调用图必须无环，故直接和间接递归都在编译期报错。`A → B → C` 合法；`A → B → A` 不合法。
- 函数可跨 tick 执行，所有 ABI 槽都必须是处理器变量或已布局的持久槽，不能依赖 Java 编译器栈。
- for 当前轮的临时 `Unit<T>` 不可直接传入、保存或从函数返回；由 `UnitSet.get(...)` 得到、或被编译器提升后的长期 Unit 句柄可作为参数和返回值，ABI 为其分配隐藏 UnitRef 槽。第一版仍不允许函数内部开启 UnitSet 遍历。
- 函数可读取在其声明前已经声明的顶层值与变量。顶层变量初始化仍按源码顺序发生；编译器沿调用图求出传递全局依赖，并拒绝任何在依赖初始化前发生的顶层调用，包括变量初始化式经函数回读自身的情况。

后续若要支持递归、回调或并发任务，必须先引入有静态深度上界的栈 ABI 和相应的物理内存预算，不能悄悄复用这套槽位。

## 两类编译器管理的存储

### 虚拟存储：静态变量槽位

`memory virtual(size: N, mode: ...)` 的单位是编译器可分配的 **静态槽位数**。一个槽位最终是一个由编译器命名的 mlog 变量；它可保存有限数值或游戏对象引用，跨 tick 存活，但会在代码重载时重置。

mlog 没有“以一个变量的数值作为另一个变量名/下标”的读取指令。因此，4096 个处理器变量不等价于一个可随意 `load(0..4095)` 的数组。对编译期已知字段偏移，编译器可以直接引用对应槽位，成本为零额外分派；对运行时索引，若强行生成跳转表会消耗标签和指令，且很快碰到 v146 的 500 标签、1000 指令上限。

因此第一版规定：虚拟存储只承载静态可寻址的局部变量、函数 ABI 槽、固定对象字段和 runtime 状态，不承诺动态数组、动态 String 缓冲或通用对象池。

### 物理存储：可索引数值槽位

`memory physical(link: "memory1", size: 512)` 对应真实的 Memory Cell/Bank。它由编译器独占管理，用户源码既没有 `Memory` 值，也没有下标读写 API。物理槽可按运行时下标读写，因而是未来数组、对象池和动态 String 地址序列的唯一通用后端。

- 一个物理槽只能保存有限数值；把对象交给 mlog `write` 会发生目标层的对象/数值转换，不能用来保存 Unit、Building、Display 或 Message 引用。
- 多块物理内存由布局器分段管理；生成的内部 `read`/`write` 负责选择正确建筑和局部地址。
- 每段会保留少量布局元数据。首次运行或布局指纹变化时，runtime 初始化自己的池和字符串元数据；布局变化不保证保留旧对象数据。
- 构建报告必须分别显示 `virtualSlots`、每块 `physicalSlots`、元数据和各模块/运行时的占用，不能只给出二者相加后的总数。

## 多处理器时的存储边界

当项目被编译为多个处理器 shard 时，以上两类存储的边界更严格：每个 shard 都有独立的处理器变量、`@counter` 和虚拟槽位，绝不通过变量名、函数 ABI 或对象引用互相访问。v146 的跨处理器协作只能通过所有参与者都已链接的真实 Memory Cell/Bank；即使后续 profile 增加读取其他处理器状态的游戏指令，MPL 也不会把它作为跨版本共享变量语义。

共享物理 Memory 不是原子的通用堆。处理器的 IPT burst 与 Building 更新顺序不属于 MPL 可依赖的调度顺序；一条 `write` 对其它处理器何时可见可能与任意其它指令交错。故共享布局只能采用编译器生成的单生产者/单消费者邮箱、单写者分区和提交版本协议；不能实现多写者队列、CAS 锁或共享自由链表。详细协议见《多处理器协作、分片与共享内存（讨论稿）》。

`memory virtual(size: ...)` 在多 shard 部署时改为每个处理器各自计量，不能把 `Main` 与 Worker 的预算相加并当作一个地址空间。物理 Memory 的容量也只按真实 Bank/Cell 计一次；多个处理器链接同一 Bank 只获得同一份共享数值槽。

`stop` 也仍是“永久停在当前处理器”的语义，不会因其他 shard 写入 Memory 而被唤醒。故多处理器 runtime 的长期 Worker 必须显式轮询邮箱；一次性 MPL 顶层程序仍只执行一次，只是协调器会在收齐 Worker 结果后发送 shutdown，再由所有 shard 停止。这个内部轮询循环不是语言级隐式 main 循环。

## `new`、数组和 String 的可实现边界

`new`、动态数组和运行时 String 拼接尚未进入当前可编译子集，但其设计不能违背上述存储模型：

- 静态对象（例如顶层 `new StatusPanel()`）可由固定字段槽实现；在对象池冻结前，不能把每次函数调用或循环中的 `new` 假装成无上限动态分配。
- 真正的对象池需要把对象句柄建模为非零 `Int`，把可动态索引的数值字段放进物理存储，并在编译期证明最大同时存活数。无法证明上界的 `new` 必须构建失败，而不是在游戏中静默耗尽。
- 第一版动态对象字段不能包含任意游戏对象引用；这类字段只能是静态槽、或改由显式的受限引用表承载。
- Unit 相关的 UnitRef 缓存、隐藏 flag tag、扫描游标和恢复元数据全是编译器私有 runtime；它们不形成 MPL 类型，也不要求用户声明容量、slot 或 `service()`。UnitRef 仅属于一个处理器，不能写入物理 Memory 或跨 shard 传递。多处理器部署中每组 Unit runtime 必须固定归属一个 shard；跨 shard 请求 API 在邮箱 ABI 完成前不开放。
- 字符输出表可以继续按 UTF-16 **代码单元**全局去重。v146 的文本缓冲上限也按 Java `StringBuilder` 的 UTF-16 长度计；一个非 BMP 字符可能占两个代码单元。
- 动态 `String` 可表示为“物理存储中的输出块地址序列 + 长度/容量”。分发器读出地址后写 `@counter` 跳入唯一的输出块，再回到分发器。它必须有固定容量和可证明的最大长度；没有上界的拼接不是合法的第一版程序。
- `Message.print(...)` 的单次可见输出上限为 400 UTF-16 代码单元。为了不把目标层截断伪装成成功，正式 String API 应要求每次 print 的静态最大长度不超过 400；超过时构建失败，或未来由显式 `printTruncated` API 表示截断意图。

## 对可空性和失败模型的影响

MPL 不实现 Rust 式运行时异常。它通过静态类型、容量证明、profile 校验和部署清单尽早拒绝可证明的问题；游戏世界的动态变化不能被伪装成编译错误。

- 数值计算必须有有限结果的明确 lowering，不能让 NaN/Infinity 落入 mlog 的 `null` 表示；精确 Int 范围、除零和 Float 非有限结果仍须在《语言规范》中冻结。
- `T?` 只用于确实可能缺失的动态对象观察结果，例如 radar/locate。链接常量本身是非空声明，但链接在游戏里失效时，控制操作只能是 best-effort；部署检查负责提前发现已知错误。
- UnitSet 的循环项在进入循环体时非空，却不代表单位永远存活或仍可控制；控制 API 是直接的 best-effort 目标层命令，不抛出 MPL 运行时异常。抢占、死亡或玩家控制只会使相应 mlog 命令不生效。

## 生成器必须检查的预算

地址解析和所有宏展开完成后，任何 target 都必须检查：

| 项目 | v146 / v159.7 基线 |
| --- | ---: |
| mlog 指令 | 不超过 1000 |
| jump label | 不超过 500 |
| 单条 mlog token | 不超过 16 |
| 单处理器图形缓冲 | 不超过 256 条 draw 命令 |
| 单 Display 已有命令 + 本次 flush | 严格小于 1024 |
| 单次 Message 可见文本 | 不超过 400 个 UTF-16 代码单元 |

超出这些限制是构建错误，不应交给游戏编辑器静默截断或替换为 InvalidStatement。
