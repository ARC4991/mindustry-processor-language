# 宏中间语言设计（讨论稿）

> 状态：MIL 的分层职责、源级定位与 `.mil` 扩展名已确认；独立 ANTLR 词法/语法入口、结构化 AST、profile 白名单、公开/运行时私有可见性、参数与代码块校验，以及公开宏到共享语义 AST/HIR/mlog 的构建链路均已实现。跨文件 import/export 链接和完整 source map 仍待实现。

## 定位

MIL 是**保留 MPL 基础语法的源级中间语言**，不是把完整 mlog 指令序列重新包装一遍的文本格式。它同时承担两个角色：

1. MPL 的编译产物：承接 UnitSet/Unit/Building runtime、字符串表和其他高级概念的降级结果；
2. 性能敏感用户可直接编写的专家语言：可绕过 MPL runtime，但仍保留结构化控制流。

`val`/`var`、表达式、普通函数调用、`if`/`while`/`for`/`break`/`continue`/`return` 等基础结构会原样保留为 MIL 节点。只有需要游戏专用实现或自动运行时的高层糖才会改写为 profile 宏调用及其显式参数。例如 `Unit.getAllDagger().where(...).take(3)` 的私有认领与遍历、`unit.move(...)` 的控制动作、字符串表输出，都在此阶段降级。

MPL 源码不出现 `@`。`@` 只属于 MIL，用于调用由 target profile 声明、映射到游戏基础能力的宏；它不是 `set`、`op`、`jump` 等每条 mlog 指令的另一种拼写。

## 两阶段编译

~~~text
MPL
  → 语义分析与高级概念降级
  → MIL（保留基础语法 + profile 宏）
  → 宏展开与目标 lowering（此时才生成标签、临时变量和目标指令）
  → 原始 mlog 指令
~~~

用户直接编写 MIL 时，跳过 MPL 的高级概念降级，从“宏展开与目标 lowering”进入流程。把 `mpl.json.entry` 指向 `src` 下的 `.mil` 文件即可直接构建；该入口会与 MPL 一样经过硬件契约、严格类型、HIR 优化、Display/Unit Runtime、内存规划和最终 target 限制校验。`mpl build` 仍会在 mlog 输出文件同目录写出规范化后的同名 `.mil`，用于检查实际进入后端的结构化程序；游戏中只粘贴 `.mlog`。

项目与包的 `src` 目录均可混合放置 `.mpl` 与 `.mil` 文件。项目加载器从 `entry` 开始递归解析相对 import，按每个文件的扩展名选择前端，并把显式 export 的函数与不可变值链接进同一个程序；依赖模块的顶层初始化按拓扑顺序执行一次，私有顶层符号彼此隔离。外部包的 registry、锁文件和 `.mplh` 资源接口合并仍待实现。每个项目/包仍各自拥有 `.mplh`：该文件只声明硬件和资源需求，不包含 MPL 或 MIL 业务代码。

## 共同的结构化核心

MPL 与 MIL 都支持变量、函数、表达式、`if`、`while`、`for`、`break`、`continue` 和 `return`。这些控制流在 MIL 中仍是结构化节点，不要求也不允许用户书写地址或标签。只有在宏展开后的目标 lowering 中，编译器才把它们变为跳转；实现可通过对 `@counter` 的写入完成间接跳转。

~~~mil
var total: Int = 1 + 2;
while (running) {
    @unit.each(@alpha, unit, @unit.alive(unit)) {
        @unit.move(unit, targetX, targetY);
    }
}
~~~

上例中 `var total: Int = 1 + 2` 与 `while` 保持基础语言写法；`@unit.each`、`@unit.alive` 与 `@unit.move` 是 profile 声明并由编译器结构化展开的游戏宏。

## 分层边界

| 能力 | MPL | MIL |
| --- | --- | --- |
| @ 宏 | 不允许 | 允许 |
| 变量、表达式、函数与结构化控制流 | 原样表达 | 原样保留 |
| Unit.getAll类型() 与私有单位 runtime | 自动降级 | 用户自行组合经 profile 允许的单位宏，或完全避免该 runtime |
| String 与字符串表 | 自动降级 | 用户直接使用经 profile 允许的输出宏；字符与槽位布局由链接器管理 |
| 原始 mlog 指令 | 不允许 | 不允许；只能调用白名单 `@` 宏 |

MIL 宏展开必须生成不会与用户变量冲突的内部标签、临时变量与内存槽位，并在诊断中保留宏调用位置。**这些内部名称、flag、owner token、UnitRef、物理地址与虚拟槽位绝不写入生成的 `.mil`**：它只显示公开宏的参数，私有实现只存在于宏展开后的内部目标 IR。

物理/虚拟内存不向 MIL 暴露：用户不能声明 Memory、传递内存给包，或直接读写槽位。宏展开所需的临时变量和内部槽位由编译器从 `.mplh` 已声明的预算中自动分配；不足时是构建期错误。

## 生成的 `.mil` 形态

由 MPL 生成的 `.mil` 应直接展示高级糖已经消失、但基础程序结构仍在的结果。例如普通算术和赋值仍是普通 MIL 语法，不会逐条改写为目标指令包装：

~~~mil
var total: Int = 1 + 2;

if (total > 0) {
    @io.print(@message1, total);
}
~~~

上例的 `@io.print` 和 `@message1` 分别表示由 profile 定义的 I/O 宏和游戏拥有的硬件链接 alias。相对地，`1 + 2`、赋值和 `if` 会继续作为 MIL 的基础节点，留到最后的 target lowering 才变为 v146/v159.7 的具体 `op`、`set`、`jump` 等 mlog 指令。`Unit.getAll类型()`、`.where(...)`、`.take(...)`、对象化 `Unit`/`Building` 操作及字符串运行时等高级糖，才会在 `.mil` 中显示为相应的公开 profile 宏调用；其 flag、owner token、UnitRef、地址和其它私有参数不属于 MIL 语法。

v146 首批公开宏目录冻结如下；未列出的 `@` 名称一律诊断为错误：

| 宏 | 形态 | 含义 |
| --- | --- | --- |
| `@unit.each` | `@unit.each(@dagger, unit, filters...) { ... }` | 遍历当前 shard 可控制的同类 Unit |
| `@unit.eachManaged` | `@unit.eachManaged(@dagger, unit, limit, filters...) { ... }` | 至多 `limit` 个 Unit 的私有稳定认领和遍历 |
| `@unit.count` | `@unit.count(@dagger, unit, filters...)` | 对惰性 Unit Set 执行一次弱一致扫描并返回数量 |
| `@unit.countManaged` | `@unit.countManaged(@dagger, unit, limit, filters...)` | 同步稳定受管 Set 并返回当前成员数 |
| `@unit.get` | `@unit.get(@dagger, unit, index, filters...)` | 扫描普通 Unit Set 并返回可空 UnitRef |
| `@unit.getManaged` | `@unit.getManaged(@dagger, unit, index, limit, filters...)` | 同步稳定受管 Set 并从当前成员中返回可空 UnitRef |
| `@unit.read` | `@unit.read(unit, health)` | 读取 profile 白名单 Unit 字段 |
| `@unit.alive` | `@unit.alive(unit)` | 读取 Unit 存活状态 |
| `@unit.move` | `@unit.move(unit, x, y)` | 对当前 Unit 下达移动控制 |
| `@unit.refRead` | `@unit.refRead(ref, health)` | 重绑保存的 UnitRef 后读取字段；失效时返回字段默认值 |
| `@unit.refAlive` | `@unit.refAlive(ref)` | 重绑保存的 UnitRef 并返回存活状态 |
| `@unit.refMove` | `@unit.refMove(ref, x, y)` | 验证非空和存活后对保存的 UnitRef 下达移动控制 |
| `@building.each` | `@building.each(@duo, building, filters...) { ... }` | 遍历 `.mplh` 中声明的同类 Building 链接 |
| `@building.count` | `@building.count(@duo, building, filters...)` | 重新执行过滤并返回匹配链接数 |
| `@building.get` | `@building.get(@duo, building, index, filters...)` | 按声明顺序返回可空 Building 引用 |
| `@building.read` | `@building.read(building, health)` | 读取 profile 白名单 Building 字段 |
| `@building.control` | `@building.control(building, action, values...)` | 调用 profile 授权的 Building 控制动作 |
| `@io.print` | `@io.print(@message1, values...)` | 向已声明 Message 顺序输出并自动 flush |
| `@io.draw` | `@io.draw(@display1, command, values...)` | 向处理器图形缓冲追加 profile 白名单绘制命令 |
| `@io.drawFlush` | `@io.drawFlush(@display1)` | Display runtime 自动插入的私有图形提交，不对应 MPL 方法 |

内容名和硬件 alias 以 `@dagger`、`@message1` 形式显式标记为游戏层符号，绝不与 MIL 变量混淆；宏名、参数类型、权限、最大资源成本和最低 target profile 由 profile 数据定义。这个目录会随新功能增加，但新增宏必须先同时拥有 profile 签名、卫生展开规则、资源成本和 v146/v159.7 测试。

生成的 `.mil` 带有“请勿直接编辑”注释，重新执行构建会覆盖它。用户手写的 `.mil` 必须位于 `src/` 并由 `mpl.json.entry` 指定，只能调用所选 profile 白名单中的公开基础宏；未知宏、Runtime 私有宏、原始 mlog、未声明硬件 alias 和错误参数都会在构建期失败。

由于 `.mil` 保留结构化控制流，通常不需要展示编译器生成的标签。宏展开与最终 target lowering 才引入标签：正常构建使用最短的 `_0`、`_1`……，`mpl build --debug ...` 则使用包含 lowering 角色的可读名称。两种模式的宏选择、指令数量与可观察行为完全相同；它们只改变最终 mlog（以及需要显示已展开 target 片段的调试输出）中的标签拼写。

## 独立语法与宏卫生（建议冻结）

MIL 不是“允许任意粘贴 mlog 的文本格式”。它拥有独立的 ANTLR 入口，但复用 MPL 的结构化块、变量、表达式、函数、类型、`if`/`while`/`for`/`break`/`continue`/`return` 语法；差异仅在于 MIL 允许 profile 白名单中的 `@` 宏调用。

~~~mil
while (running) {
    @unit.each(@alpha, unit) {
        @unit.move(unit, targetX, targetY);
    }
}
~~~

- 用户不能定义宏、标签、原始 `@counter` 跳转、Memory 读写或保留字段写入；这些仍由编译器/runtime 独占。
- 每个宏由 target profile 提供签名、参数类型、权限、可能的暂停/控制副作用、临时槽需求和最低版本。普通处理器调用 worldOnly 宏是构建错误，不留给游戏解析器替换为 InvalidStatement。
- 宏展开通过内部 `SymbolId` 分配临时变量、标签和物理槽，而不是用用户可猜测的文本前缀。用户变量也会在链接时按模块符号重新命名，因此两个包、两个宏展开和用户源码不会发生捕获。
- 宏只接收显式的实参符号；它不能通过字符串拼接捕获调用方变量，也不能声明跨展开可见的全局名称。
- 展开结果保留“调用点 → 宏节点 → mlog 指令”的来源链。若超过 token、标签、指令或资源预算，诊断首先指向 MIL 宏调用点，并附带展开后的成本。

MPL 自动生成的 MIL 与用户 `.mil` 必须经过同一 profile 校验、资源链接器和最终 mlog 限制校验。性能敏感用户可以绕过高层 runtime，但不能绕过权限、硬件契约、flag 保留规则或内存预算。
