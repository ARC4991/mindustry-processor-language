# 目标版本与优化策略（讨论稿）

> 状态：已确认支持 v146 与 v159.7；profile、构建报告和部署清单的第一版 JSON schema 已冻结，完整内容表仍待从源码生成。

## 核心原则

MPL 的语义先独立于具体 mlog 指令定义，再由 target profile 选择生成方式。游戏加入新处理器指令时，不修改已有 MPL 程序的含义；编译器可以在新 profile 中用它生成更短、更快的 mlog。

```text
MPL / MIL
  → 与版本无关的高层 IR
  → target profile 能力检查
  → 选择 baseline 或专用 lowering
  → 目标版本的 mlog
```

例如，MPL 条件表达式在 v146 生成临时变量和跳转，在 v159.7 可降级为 `select`。两种产物的可观察结果必须相同。

## 构建与兼容性

- 每次构建显式指定一个精确 target，例如 `v146` 或 `v159.7`；不会生成“运行时自动识别游戏版本”的 mlog。
- 项目可以对多个 target 分别构建，得到多个 mlog 产物。
- 包声明自己的最低 target 能力；链接器计算项目 target 与全部依赖的交集。若某包需要 v159.7 专属能力，面向 v146 构建时直接报错。
- 未声明版本专属能力的包应保持可移植：它可以在多个 profile 构建，由各 profile 独立优化。
- target profile 还决定内容类型、senseable 属性、指令参数、硬件容量和特权限制；不能只把它当作“是否认识一条指令”的开关。
- profile 还可声明运行期部署前提（例如地图规则 `logicUnitControl`）。它们不属于语言运行时错误：构建报告与部署校验必须明确列出，不能静默降级。

## 专用优化的准入条件

一项 profile 专用 lowering 必须同时满足：

1. 与 baseline lowering 的 MPL 可观察语义等价，包括副作用顺序、null 行为、输出截断和跨 tick 行为；
2. 不要求用户修改源代码、包硬件声明或内存预算；
3. 不把 worldOnly/clientOnly 指令用于普通处理器；
4. 在构建报告中记录使用的优化和节省的估计指令数；
5. 有 baseline 与专用 lowering 的同一测试用例，分别在各自 profile 的预期 mlog 上验证。

这样，新游戏版本可以提升性能，而不会把“升级游戏后程序悄悄变了”带入语言语义。

## v146 / v159.7 的首批 lowering 选择

| 高层 IR | v146 | v159.7 |
| --- | --- | --- |
| 条件选择 | 条件跳转 + 赋值 | `select`，仅限分支均无副作用且已求值 |
| 动态字符输出 | 全局去重的字符输出跳转表 | `printchar`，仅限一个已证明范围内的 UTF-16 代码单元 |
| 受限格式化输出 | 字符串 runtime / 连续 print | `format`，仅在等价时启用 |
| 颜色分量拆解 | 位/算术展开 | `unpackcolor` |
| 多处理器邮箱 | 共享 Memory 的 SPSC 读写与版本提交 | 可在完全等价时使用已链接 LogicBuild 的变量读写；共享 Memory 仍是 ABI |

`draw print`、Query、天气、音频、标记等没有 v146 的等价普通处理器能力。因此它们应作为未来显式声明最低 target 为 v159.7 的 API，而不是优化已有跨版本 API。

## profile 数据的生成与审查

每个 profile 由机器可读描述和来源说明组成，结构见《[Profile 与构建产物 Schema（讨论稿）](数据格式/Profile与构建产物Schema（讨论稿）.md)》。建议从对应版本源码提取并人工审查：

- `LStatements` / `LExecutor`：指令、参数、输出、限制与特权边界；
- `LAccess`、`LUnitControl`、雷达和 locate 枚举：属性与控制 API；
- `Blocks`、Logic Display、Memory、Message 实现：硬件类型和容量；
- 内容注册表：Unit、Block、Item、Liquid 等可用类型。

profile 变更必须是独立提交，并包含与前一 profile 的差异报告；新指令首先进入能力表，之后才决定是否暴露为 MPL API 或仅用作优化。
