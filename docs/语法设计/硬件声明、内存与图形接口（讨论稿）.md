# 硬件声明、内存与图形接口（讨论稿）

> 状态：`.mplh` 只包含硬件相关声明、内存不向 MPL/MIL 源码暴露、组合屏幕与 print 自动刷新已确认。单处理器仍是默认部署；多处理器拓扑、共享 Memory 绑定和部署清单已确定方向，声明关键字的最终拼写待实现时冻结。

## 硬件声明文件

每个项目有且仅有一个专用硬件声明文件，建议扩展名为 `.mplh`。它不包含业务逻辑，只允许硬件相关的声明语句：`processor ...`、`link(...)`、`Display.combine(...)`、`memory physical(...)`、`memory virtual(...)` 及包端的 `require ...`。变量、函数、类、控制流、`import/export`、普通表达式和 MIL 的 `@` 宏均不允许出现在 `.mplh`。

项目 `.mplh` 将处理器链接的游戏建筑声明为导出的特殊常量；普通 MPL/MIL 模块可直接使用这些非内存硬件常量，而不直接依赖链接编号，从而与地图硬件解耦。内存声明不产生可被源码读写的对象；多处理器时它可有仅供部署清单使用的逻辑名称。

这里的“解耦”只发生在 MPL 源码层：`link("message1")` 中的 `message1` 是游戏自动生成的 mlog 链接 alias，不是永久物理 ID。它仍是正式且推荐的绑定方式：相比 `getlink` 的顺序下标，它可读、可写入声明，也不会因源码中其它链接的取用顺序而改变。拆除、重连、超出范围或同类链接变化后，alias 仍可能改变，甚至退化为一个普通 mlog 变量。因此 `.mplh` 是**部署期硬件契约**；构建产物必须记录 MPL 名称、期望 alias、期望类型和读写权限，未来 `mpl hardware check` 在安装时核对它们。

以下是建议语法：

~~~mpl
// 硬件声明文件（文件名待定）
const TopLeft: Display = link("display1");
const TopRight: Display = link("display2");
const BottomLeft: Display = link("display3");
const BottomRight: Display = link("display4");

export const MainScreen: Display = Display.combine([
    [TopLeft, TopRight],
    [BottomLeft, BottomRight]
]);

export const AlertBoard: Message = link("message1");
memory physical(
    link: "memory1",
    size: 512
);
memory virtual(
    size: 4096,
    mode: Pool
);
export const LaunchSwitch: Switch = link("switch1");
~~~

`link("message1")` 绑定的是游戏处理器提供的 mlog 链接 alias，而非 MPL 变量名或不可见链接序号。`link(...)` 仅存在于 `.mplh` 硬件声明层，普通 MPL/MIL 不能调用它。上述示例声明的预算上限为 512 个物理数值槽和 4096 个静态变量槽；它们不能简单相加成“4608 个等价内存单元”。构建报告必须同时显示总量、已用量及物理/虚拟的明细。

`link(...)`、`Display.combine(...)` 与两种 `memory` 声明仅能在硬件声明文件中使用。这里导出的 `const` 仅用于 Display、Message、Switch 等非内存硬件；它们在编译期绑定类型和链接位置，不能在普通代码中重新赋值。

### `.mplh` 暂定文法

~~~ebnf
硬件文件      = { 项目硬件声明 | 包资源需求 }, EOF ;
项目硬件声明  = 处理器声明 | 硬件常量 | 物理内存声明 | 虚拟内存声明 ;
处理器声明    = "processor", 标识符, [ "[", 整数, "]" ], ":", 处理器类型, ";" ;
硬件常量      = [ "export" ], "const", 标识符, ":", 硬件类型, "=", 硬件构造式, ";" ;
硬件构造式    = "link", "(", 字符串, ")" | "Display.combine", "(", 显示矩阵, ")" ;
物理内存声明  = "memory", "physical", [ 标识符 ], "(",
                  ( "link", ":", 字符串, "," | "links", ":", "{", 内存绑定, { ",", 内存绑定 }, "}", "," ),
                  "size", ":", 整数, ")", ";" ;
内存绑定      = 处理器选择器, ":", "link", "(", 字符串, ")" ;
虚拟内存声明  = "memory", "virtual", "(", [ "on", ":", 处理器选择器, "," ],
                  "size", ":", 整数, ",", "mode", ":", 标识符, ")", ";" ;
处理器选择器  = 标识符, [ "[", ( 整数 | "*" ), "]" ] ;
包资源需求    = "require", "memory", ( "physical" | "virtual" ), "(", 需求参数, ")", ";"
                | "require", 标识符, ":", 硬件类型, "(", 需求参数, ")", ";" ;
需求参数      = 标识符, ":", ( 整数 | 标识符 ), { ",", 标识符, ":", ( 整数 | 标识符 ) } ;
~~~

语义限制：项目 `.mplh` 只能包含项目硬件声明，包 `.mplh` 只能包含包资源需求；二者都不允许任何业务语句。上表中的 `memory` 与 `require` 是 `.mplh` 专用关键字，不属于 MPL/MIL 源码。

## 多处理器与共享 Memory

未写 `processor` 时，项目等价于一个隐式的 `Main: Logic`，现有单处理器 `memory` 写法保持兼容。声明了多个处理器后，每一个处理器都有自己的变量槽、`@counter`、函数 ABI 与虚拟内存预算；`memory virtual(on: Worker[*], ...)` 是给每个 Worker 实例分别分配预算，不是把多个处理器变量拼成一个数组。

共享物理段使用逻辑名和每个处理器的本地 alias。例如：

~~~mpl
processor Main: Hyper;
processor Worker[2]: Logic;

memory virtual(on: Main, size: 1024, mode: Pool);
memory virtual(on: Worker[*], size: 384, mode: Static);

memory physical Shared(
    size: 512,
    links: {
        Main: link("memory1"),
        Worker[*]: link("memory1")
    }
);
~~~

`Shared` 不会泄漏到 MPL/MIL；它要求部署清单中的这些本地 alias 指向同一个真实 Memory Cell/Bank，并由启动握手实际确认。多次链接同一 Bank 不会把 512 槽乘以处理器数量。共享段只能被编译器生成的、具有单写者所有权的通信协议访问；用户和包都不能取得它的地址或 `[]` 访问。完整的分片、启动握手、SPSC 邮箱与 I/O 所有权规则见《多处理器协作、分片与共享内存（讨论稿）》。

## 组合屏幕

Display.combine(...) 接受二维矩阵。2 × 2 的四块屏幕、3 × 3 的九块屏幕等都被视为一个逻辑 Display：

~~~mpl
const MainScreen: Display = Display.combine([
    [Screen0, Screen1, Screen2],
    [Screen3, Screen4, Screen5],
    [Screen6, Screen7, Screen8]
]);

const width: Int = MainScreen.width;
const height: Int = MainScreen.height;
~~~

编译器在编译期验证矩阵为矩形、每格均为兼容屏幕，并从组成屏幕推导 width 和 height。组合 Display 的绘制命令被降级为各物理屏幕的绘制和刷新；因此组合规模会线性增加输出指令数。坐标转换、跨屏幕图元的裁剪及不同规格屏幕混排需要原型验证。

## 物理内存与虚拟内存

### 物理内存

`memory physical(...)` 对应真实链接的 Memory Cell 或 Memory Bank。容量与链接位置由 `.mplh` 在编译期声明，但不会产生 `Data` 一类可被源码引用的对象。v146 的 Cell/Bank 容量分别是 64/512；`size` 是部署时必须匹配的断言，而不是让编译器把任意链接伪装成该容量。

物理内存是 compiler runtime 唯一通用的运行时可索引数值存储：数组、对象池字段、动态 String 的输出块地址序列和池元数据都必须由内部 `read`/`write` 管理。一个槽只能保存有限数值，不能持久保存 Unit、Building、Display 或 Message 等对象引用。

若任一物理段或虚拟段无法满足后端布局约束，构建直接失败并报告各模块/包的占用来源；不存在“动态下标越界”或“内存耗尽”的运行时错误，因为用户不能对物理内存做下标读写。每个物理段会预留布局指纹和 runtime 元数据；布局指纹变化时，编译器生成的初始化流程可以重置自己的数据，不承诺保留旧对象/字符串内容。

### 虚拟内存

`memory virtual(...)` 不绑定游戏内存建筑。它定义编译器可使用的处理器内部**静态变量槽**预算，是函数局部变量、固定字段、返回地址和 runtime 续执行状态的存储基础。它不应被误解为独立的目标虚拟机或额外硬件。

处理器变量可保存对象引用，但 mlog 没有按运行时变量名/下标间接读取另一个变量的指令。因此 4096 个虚拟槽不等于可随意索引的 4096 项数组：已知字段偏移可直接访问，动态下标若用跳转表实现会消耗指令和标签，并受 v146 的 1000 指令、500 标签限制。动态数组、对象池和运行时 String 序列必须优先放入物理存储，不能只靠虚拟槽承诺实现。

编译器统一命名和分配虚拟存储，防止模块、包、字符串 runtime 与单位 runtime 相互冲突，并在构建报告中显示其使用量。处理器代码重载会重置虚拟槽；物理 Memory 内容不会自动清零。物理内存与虚拟内存都不具有 MPL/MIL 的 `Memory` 类型、变量名或 `[]` 操作；在 `.mpl`、`.mil` 或包源码中写任何内存读写都是编译错误。

虚拟内存也必须声明 `size`，以便编译器静态分配变量槽。初始管理模式中，`Static` 用于固定运行时槽位；`Pool` 仅表示链接器允许为固定、可证明上界的对象元数据预留槽，真正可索引的对象字段仍须落在物理存储；`Manual` 预留给未来受控的底层编译器功能，不对用户源码开放。

## 图形与文本对象接口

Display 与 Message 是硬件对象。文本输出由 Message 管理并自动刷新：

~~~mpl
AlertBoard.print("敌人数量：", enemyCount);
// 编译器在本次调用结尾自动输出 printflush(AlertBoard)
~~~

Display 提供接近 HTML5 Canvas 的基础绘制接口：

~~~mpl
MainScreen.clear(Color.black);
MainScreen.fill(Color.green);
MainScreen.fillRect(8, 8, 40, 20);
MainScreen.stroke(Color.white);
MainScreen.strokeRect(8, 8, 40, 20);
MainScreen.line(0, 0, MainScreen.width, MainScreen.height);
MainScreen.flush();
~~~

第一版只对目标 draw 指令提供一对一或接近一对一的封装；clear、fill、stroke、矩形、线和 flush 是优先范围。复杂路径、字体、图像、变换栈和保留式画布不在第一版承诺中。

## 资源独占与包

硬件声明的导出常量自动对项目 MPL/MIL 代码可见，不需要特别 import。包不能硬编码 link 编号、内存地址或组合屏幕布局；包通过 `import ... with {...}` 接收调用方传入的 Display、Message 等非内存硬件常量。包的内存预算从其自身 `.mplh` 自动汇总，不能由调用方手工传入。若同一可写硬件被多个模块写入，声明文件或构建配置应显式标注其共享/独占策略；编译器至少应给出冲突警告。
