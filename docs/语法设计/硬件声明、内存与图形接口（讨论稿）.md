# 硬件声明、内存与图形接口（讨论稿）

> 状态：`.mplh` 只包含蓝图外硬件声明；处理器、Memory 与内部连接由编译器自动规划。根项目 `const/link`、组合 Display、包 `require` 与 `with` 传递注入均已接入编译和部署产物。组合屏当前只接受 profile 已知、同规格、无重复成员的矩形矩阵。

## 硬件声明文件

每个项目有且仅有一个专用硬件声明文件，建议扩展名为 `.mplh`。它不包含业务逻辑，只允许蓝图外硬件相关的声明语句：`link(...)`、`Display.combine(...)` 及包端的 `require ...`。处理器、物理 Memory、虚拟槽位和内部连接由编译器自动规划，不属于 `.mplh`。变量、函数、类、控制流、普通表达式和 MIL 的 `@` 宏均不允许出现在 `.mplh`。

项目 `.mplh` 将处理器链接的游戏建筑声明为导出的特殊常量；普通 MPL/MIL 模块可直接使用这些硬件常量，而不直接依赖链接编号，从而与地图硬件解耦。Memory 声明不会出现在项目或包源码中；编译器按最终 HIR/MIL 和全部依赖统一规划其数量、容量、内部 alias 与位置。`require` 只能描述外部硬件，根项目在链接时必须按类型、权限、数量和组合屏矩阵严格满足，不能用近似类型或多余/缺失硬件降级通过。

多处理器构建可选生成的蓝图只放置处理器和真实 Memory Cell/Bank。`Display`、`Message`、`Switch` 及其它 `link(...)` 建筑是地图业务硬件：它们**不属于蓝图**，由玩家自行放置并连接；构建产物只把它们记录为部署期外部硬件契约。这样蓝图可以随计算规模复用，而不强迫项目占用或复制地图的业务布局。

运行时布局默认由编译器自动选择，但项目可在 `mpl.json` 约束可使用的处理器与目标。它不能指定坐标、link alias 或手工 Memory 数量：

```json
"runtime": {
  "goal": "minResources",
  "processors": { "micro": 2, "logic": 1, "hyper": 0 },
  "memory": { "cell": 4, "bank": 2 }
}
```

`goal` 可为 `minResources`（默认，优先较低制造成本的处理器）、`balanced`、`maxPerformance`。`processors` 与 `memory` 的值是每种类型的数量上限：`0` 禁止该类型，正整数允许并限制数量；不写 `runtime` 则使用编译器默认策略。后端真正需要动态物理存储时，规划器才会根据这些约束放入 Cell/Bank 并写入处理器内部 link。仅使用静态下标的基础项目不会凭空生成 Memory；受证明动态 Array 会按实际容量规划 Cell/Bank。

这里的“解耦”只发生在 MPL 源码层：`link("message1")` 中的 `message1` 是游戏自动生成的 mlog 链接 alias，不是永久物理 ID。它仍是正式且推荐的绑定方式：相比 `getlink` 的顺序下标，它可读、可写入声明，也不会因源码中其它链接的取用顺序而改变。拆除、重连、超出范围或同类链接变化后，alias 仍可能改变，甚至退化为一个普通 mlog 变量。因此 `.mplh` 是**部署期硬件契约**；构建产物必须记录 MPL 名称、期望 alias、期望类型和读写权限，未来 `mpl hardware check` 在安装时核对它们。

以下是建议语法：

~~~mpl
// 硬件声明文件（文件名待定）
const TopLeft: Display = link("display1", width: 80, height: 80);
const TopRight: Display = link("display2", width: 80, height: 80);
const BottomLeft: Display = link("display3", width: 80, height: 80);
const BottomRight: Display = link("display4", width: 80, height: 80);

export const MainScreen: Display = Display.combine([
    [TopLeft, TopRight],
    [BottomLeft, BottomRight]
]);

export const AlertBoard: Message = link("message1");
export const LaunchSwitch: Switch = link("switch1");
~~~

`link("message1")` 绑定的是游戏处理器提供的 mlog 链接 alias，而非 MPL 变量名或不可见链接序号。`link(...)` 仅存在于 `.mplh` 硬件声明层，普通 MPL/MIL 不能调用它。实际的物理与虚拟存储预算由编译器从最终 HIR 推导；它们不能相加成一种等价内存。构建报告必须同时显示两类存储的总量与已用量。

`Display` 是 MPL 的显示接口类型，不等同于单一游戏方块名。v146 与 v159.7 profile 当前登记 `logic-display` 的 80×80 和 `large-logic-display` 的 176×176 两种静态规格；`link(...)` 的 width/height 必须恰好匹配其中一种。未写尺寸的直接 Display 仍可用于绘图，但不能读取 `.width/.height`、参加组合或满足包的最小尺寸约束。

`link(...)`、`Display.combine(...)` 与两种 `memory` 声明仅能在硬件声明文件中使用。这里导出的 `const` 仅用于 Display、Message、Switch 等非内存硬件；它们在编译期绑定类型和链接位置，不能在普通代码中重新赋值。

### `.mplh` 暂定文法

~~~ebnf
硬件文件      = { 项目硬件声明 | 包资源需求 }, EOF ;
项目硬件声明  = 硬件常量 ;
硬件常量      = [ "export" ], "const", 标识符, ":", 硬件类型, "=", 硬件构造式, ";" ;
硬件构造式    = "link", "(", 字符串, [ ",", "width", ":", 整数, ",", "height", ":", 整数 ], ")"
                | "Display.combine", "(", 显示矩阵, ")" ;
包资源需求    = "require", 标识符, ":", 硬件类型, "(", 需求参数, ")", ";" ;
需求参数      = 标识符, ":", ( 整数 | 标识符 ), { ",", 标识符, ":", ( 整数 | 标识符 ) } ;
~~~

语义限制：项目 `.mplh` 只能包含项目硬件声明，包 `.mplh` 只能包含包资源需求；二者都不允许任何业务语句。包需求可描述最低资源能力，但不能指定实际 Memory、处理器或 alias；全局链接器按最终 HIR 自动规划。`require` 不属于 MPL/MIL 源码。

当前 `require` 参数支持 `access: read|write|readWrite`、`count: 1`、`minWidth` 和 `minHeight`。同名需求可分多条累积，类型和 access 不能冲突；最小尺寸取最严格值。Memory、处理器和未知参数会在安装期失败。包 import 时使用规范化后的逻辑 Display 尺寸检查 `minWidth`/`minHeight`；尺寸未知或任一方向不足均报告 `MPL1416`。

## 多处理器与共享 Memory

当前实现生成一个隐式 `Main` shard，处理器类型由 `mpl.json` 的 runtime 约束自动选择。未来启用多处理器分片时，处理器数量、类型、程序切分、本地变量和共享 Memory 都由编译器根据指令上限与数据流自动规划；`.mplh` 不接受 `processor` 或 `memory` 声明。

共享段的 alias、本地绑定和单写者所有权仅出现在编译器布局与部署清单中，不会泄漏到 MPL/MIL。多次链接同一 Bank 不会把 512 槽乘以处理器数量。完整的分片、启动握手、SPSC 邮箱与 I/O 所有权规则见《多处理器协作、分片与共享内存（讨论稿）》。

## 组合屏幕

Display.combine(...) 接受二维矩阵。2 × 2 的四块屏幕、3 × 3 的九块屏幕等都被视为一个逻辑 Display：

~~~mpl
const MainScreen: Display = Display.combine([
    [Screen0, Screen1, Screen2],
    [Screen3, Screen4, Screen5],
    [Screen6, Screen7, Screen8]
]);

const width: Int = MainScreen.width;
const height: Int = MainScreen.height;
~~~

编译器在编译期验证矩阵为非空矩形、每格尺寸已知且规格一致，并拒绝重复使用同一物理屏幕。width 和 height 由展开后的物理 tile 推导；嵌套组合会被扁平化。组合 Display 的绘制命令按逻辑批次复制到每块物理屏幕，坐标减去 tile 原点后由目标 Display 视口裁剪，因此跨屏矩形和线段能够连续显示。每个非平凡动态参数在分发前只求值一次。组合规模会线性增加 draw、坐标换算和 flush 指令数；异规格混排尚不支持。

## 物理内存与虚拟内存

### 物理内存

物理 Memory 由编译器根据最终 HIR 需求自动放置到运行时蓝图，不在 `.mplh`、MPL 或 MIL 中声明。v146 的 Cell/Bank 容量分别是 64/512；`mpl.json` 只能限制每种块的最大数量，不能指定容量、地址、alias 或布局。

物理内存是 compiler runtime 唯一通用的运行时可索引数值存储：数组、对象池字段、动态 String 的输出块地址序列和池元数据都必须由内部 `read`/`write` 管理。一个槽只能保存有限数值，不能持久保存 Unit、Building、Display 或 Message 等对象引用。

若任一物理段或虚拟段无法满足后端布局约束，构建直接失败并报告各模块/包的占用来源；不存在“动态下标越界”或“内存耗尽”的运行时错误，因为用户不能对物理内存做下标读写。每个物理段会预留布局指纹和 runtime 元数据；布局指纹变化时，编译器生成的初始化流程可以重置自己的数据，不承诺保留旧对象/字符串内容。

### 虚拟内存

虚拟内存是编译器自动命名和计量的处理器内部**静态变量槽**，是函数局部变量、固定字段、返回地址和 runtime 续执行状态的存储基础。它不在源码或 `.mplh` 中声明，也不是独立的目标虚拟机或额外硬件。

处理器变量可保存对象引用，但 mlog 没有按运行时变量名/下标间接读取另一个变量的指令。因此 4096 个虚拟槽不等于可随意索引的 4096 项数组：已知字段偏移可直接访问，动态下标若用跳转表实现会消耗指令和标签，并受 v146 的 1000 指令、500 标签限制。动态数组、对象池和运行时 String 序列必须优先放入物理存储，不能只靠虚拟槽承诺实现。

编译器统一命名和分配虚拟存储，防止模块、包、字符串 runtime 与单位 runtime 相互冲突，并在构建报告中显示其使用量。处理器代码重载会重置虚拟槽；物理 Memory 内容不会自动清零。物理内存与虚拟内存都不具有 MPL/MIL 的 `Memory` 类型、变量名或 `[]` 操作；在 `.mpl`、`.mil` 或包源码中写任何内存读写都是编译错误。

虚拟槽也由编译器按变量、函数 ABI 和 runtime 状态自动计量，用户不声明 `size` 或管理模式。未来引入对象池时，最大同时存活数仍必须由编译器证明；不会因为自动规划而允许无上界分配。

## 图形与文本对象接口（已确认的第一版）

Display 与 Message 是硬件对象。文本输出由 Message 管理并自动刷新：

~~~mpl
AlertBoard.print("敌人数量：", enemyCount);
// 编译器在本次调用结尾自动输出 printflush(AlertBoard)
~~~

已由当前编译器实现的直接链接建筑 API 是 profile 驱动且强类型的：读取声明建筑的白名单字段会生成 `sensor`，调用其白名单控制方法会生成固定宽度的 `control`。例如：

~~~mpl
// hardware.mplh：const LaunchSwitch: Switch = link("switch1");
//                 const Gun: Duo = link("duo1");
val enabled: Bool = LaunchSwitch.enabled;
LaunchSwitch.setEnabled(!enabled);
Gun.shoot(targetX, targetY, true);
~~~

`LaunchSwitch`、`Gun` 和 `switch1`/`duo1` 不会被当作 MPL 变量或数字。前者只能来自 `.mplh` 的 `const ... = link(...)`，后者仅在生成的 mlog/MIL 的 `@` 硬件层出现。字段、动作名、参数类型都以选定 target profile 为准；未声明的硬件、错误的字段或动作、以及把硬件作为数值使用，都会在编译期失败。

当前已实现**直接声明链接**的读取和控制、单块与组合 `Display` 的基础绘制 lowering，以及按具名链接静态展开的 `Building.getAll类型()`。组合 Display 的物理 tile、逻辑尺寸和坐标写入格式化的 `deployment.json`，连接说明同时列出物理 alias 与逻辑组成关系。

Display 提供接近 HTML5 Canvas 的基础绘制接口：

~~~mpl
MainScreen.clear(Color.black);
MainScreen.fill(Color.green);
MainScreen.fillRect(8, 8, 40, 20);
MainScreen.stroke(Color.white);
MainScreen.strokeRect(8, 8, 40, 20);
MainScreen.line(0, 0, MainScreen.width, MainScreen.height);
~~~

绘制可以直接放在循环中，用户不需要也不能手动刷新：

~~~mpl
var x: Int = 0;
while (true) {
    MainScreen.clear(Color.black);
    MainScreen.fill(Color.green);
    MainScreen.fillRect(x, 8, 12, 12);
    x = (x + 1) % MainScreen.width;
}
~~~

`Color` 是不透明值类型，只能由 profile 提供的常量（如 `Color.black`）或 `Color.rgb(red, green, blue[, alpha])` 构造；四个分量都是 `Int`，运行时按 `0..255` 饱和。`clear(color)`、`fill(color)`、`stroke(color)`、`fillRect(...)`、`strokeRect(...)` 与 `line(...)` 都只向处理器的**全局绘图缓冲**追加命令；`fill` / `stroke` 改变后续图元的颜色状态，`clear` 在提交时先清空目标屏幕。

`flush()` **不属于 MPL API**，也不能由用户调用。Display runtime 在 HIR 中插入私有提交节点，只在生成的 MIL 中体现为 `@io.drawFlush(@display1)`，最终 mlog 则出现 `drawflush display1`。它会在切换 Display、结构化控制流的每条退出路径、循环回边、函数结束和顶层结束前提交当前缓冲；因此 `while`、`for`、Unit/Building 遍历和函数内的绘制都被允许，每次循环迭代不会累积前一次的 draw 命令。编译时会合并同一 Display 的相邻绘制，达到当前 profile 的 256 条缓冲上限时自动分段提交，切换 Display 时先提交旧目标，没有待提交命令时不生成刷新指令。

Display runtime 保证一次 `drawflush` 最多携带 profile 允许的 256 条 v146 draw 命令。目标 Display 已有命令与本次命令之和仍必须严格小于 1024；这是地图状态，编译期不能凭空证明。需要保留式画面的代码应在一帧的开头调用 `clear(...)`，让目标层按游戏规则清空旧命令。坐标沿用 Mindustry Display 的左下角原点；组合矩阵仍按源码从上到下书写，编译器会把首行放在逻辑画布最高的 y 区域。当前编译器只做 tile 原点平移，坐标打包范围和负尺寸行为沿用选定 target，不额外承诺 Canvas 风格的几何规范化。

组合屏幕按声明矩阵从左到右、从上到下拼接。一个刷新边界内的逻辑命令保持源码顺序，并按 tile 成批重放；每块物理屏幕恰好提交一次，`fill`/`stroke` 状态会与其后图元一起到达同一缓冲。异规格屏幕混排仍在编译期拒绝。复杂路径、字体、图像、变换栈和保留式画布不在第一版承诺中。

## 资源独占与包

硬件声明的导出常量自动对项目 MPL/MIL 代码可见，不需要特别 import。包不能硬编码 link 编号、内存地址或组合屏幕布局；包通过 `import ... with {...}` 接收调用方传入的 Display、Message 等非内存硬件常量。包的内存预算从其自身 `.mplh` 自动汇总，不能由调用方手工传入。同一可写硬件可由同一 shard 内的多个模块按源码链接顺序写入，但不能由两个 shard 写入；后者是构建错误而非警告。
