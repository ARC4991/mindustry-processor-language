# 硬件声明、内存与图形接口（讨论稿）

> 状态：`.mplh` 只包含硬件相关声明、内存不向 MPL/MIL 源码暴露、组合屏幕与 print 自动刷新已确认；声明关键字的最终拼写待冻结。

## 硬件声明文件

每个项目有且仅有一个专用硬件声明文件，建议扩展名为 `.mplh`。它不包含业务逻辑，只允许硬件相关的声明语句：`link(...)`、`Display.combine(...)`、`memory physical(...)`、`memory virtual(...)` 及包端的 `require ...`。变量、函数、类、控制流、`import/export`、普通表达式和 MIL 的 `@` 宏均不允许出现在 `.mplh`。

项目 `.mplh` 将处理器链接的游戏建筑声明为导出的特殊常量；普通 MPL/MIL 模块可直接使用这些非内存硬件常量，而不直接依赖链接编号，从而与地图硬件解耦。内存声明没有源码名称。

以下是建议语法：

~~~mpl
// 硬件声明文件（文件名待定）
const TopLeft: Display = link(0);
const TopRight: Display = link(1);
const BottomLeft: Display = link(2);
const BottomRight: Display = link(3);

export const MainScreen: Display = Display.combine([
    [TopLeft, TopRight],
    [BottomLeft, BottomRight]
]);

export const AlertBoard: Message = link();
memory physical(
    link: 5,
    size: 512
);
memory virtual(
    size: 4096,
    mode: Pool
);
export const LaunchSwitch: Switch = link(6);
~~~

`link()` 不要求用户填写不可见的链接序号。第一版按游戏默认链接名绑定：唯一的 Message 会降级为 `message1`。需要精确指定时可写 `link("message2")`；后续会提供硬件导出/检查流程来自动生成这部分声明。上述声明的总可分配内存预算为 `512 + 4096 = 4608`。`physical` 与 `virtual` 只描述后端的存放位置和布局策略，不把容量分割成互不相干的语言层资源；构建报告应同时显示总量、已用量及物理/虚拟的明细。

`link(...)`、`Display.combine(...)` 与两种 `memory` 声明仅能在硬件声明文件中使用。这里导出的 `const` 仅用于 Display、Message、Switch 等非内存硬件；它们在编译期绑定类型和链接位置，不能在普通代码中重新赋值。

### `.mplh` 暂定文法

~~~ebnf
硬件文件      = { 项目硬件声明 | 包资源需求 }, EOF ;
项目硬件声明  = 硬件常量 | 物理内存声明 | 虚拟内存声明 ;
硬件常量      = [ "export" ], "const", 标识符, ":", 硬件类型, "=", 硬件构造式, ";" ;
硬件构造式    = "link", "(", [ 字符串 ], ")" | "Display.combine", "(", 显示矩阵, ")" ;
物理内存声明  = "memory", "physical", "(", "link", ":", 整数, ",", "size", ":", 整数, ")", ";" ;
虚拟内存声明  = "memory", "virtual", "(", "size", ":", 整数, ",", "mode", ":", 标识符, ")", ";" ;
包资源需求    = "require", "memory", ( "physical" | "virtual" ), "(", 需求参数, ")", ";"
                | "require", 标识符, ":", 硬件类型, "(", 需求参数, ")", ";" ;
需求参数      = 标识符, ":", ( 整数 | 标识符 ), { ",", 标识符, ":", ( 整数 | 标识符 ) } ;
~~~

语义限制：项目 `.mplh` 只能包含项目硬件声明，包 `.mplh` 只能包含包资源需求；二者都不允许任何业务语句。上表中的 `memory` 与 `require` 是 `.mplh` 专用关键字，不属于 MPL/MIL 源码。

## 组合屏幕

Display.combine(...) 接受二维矩阵。2 × 2 的四块屏幕、3 × 3 的九块屏幕等都被视为一个逻辑 Display：

~~~mpl
const MainScreen: Display = Display.combine([
    [Screen0, Screen1, Screen2],
    [Screen3, Screen4, Screen5],
    [Screen6, Screen7, Screen8]
]);

const width: Int = MainScreen.width;
const height: Int = MainScreen.height;
~~~

编译器在编译期验证矩阵为矩形、每格均为兼容屏幕，并从组成屏幕推导 width 和 height。组合 Display 的绘制命令被降级为各物理屏幕的绘制和刷新；因此组合规模会线性增加输出指令数。坐标转换、跨屏幕图元的裁剪及不同规格屏幕混排需要原型验证。

## 物理内存与虚拟内存

### 物理内存

`memory physical(...)` 对应真实链接的内存单元或内存库。容量与链接位置由 `.mplh` 在编译期确定，但不会产生 `Data` 一类可被源码引用的对象。编译器把所有需要持久存储的内容——对象字段、字符串序列、runtime 元数据和包的存储需求——统一布局到已声明的物理容量中。

若全局总需求超过 `physical.size + virtual.size`，或任一部分无法满足其后端布局约束，构建直接失败并报告各模块/包的占用来源；不存在“动态下标越界”或“内存耗尽”的运行时错误，因为用户不能对物理内存做下标读写。

### 虚拟内存

`memory virtual(...)` 不绑定游戏内存建筑。它定义编译器可使用的处理器内部变量预算，是函数局部变量、类字段、字符串表索引和 runtime 元数据的存储基础。它不应被误解为独立的目标虚拟机或额外硬件。

编译器统一命名和分配虚拟内存，防止模块、包、字符串 runtime 与单位 runtime 相互冲突，并在构建报告中显示其使用量。物理内存与虚拟内存都不具有 MPL/MIL 的 `Memory` 类型、变量名或 `[]` 操作；在 `.mpl`、`.mil` 或包源码中写任何内存读写都是编译错误。

虚拟内存也必须声明 `size`，以便编译器静态分配变量和对象池。初始管理模式保留 Static、Pool 与 Manual，作为链接器的内部布局策略：Static 用于固定运行时槽位，Pool 用于 `new/delete` 对象池，Manual 预留给未来受控的底层编译器功能，不对用户源码开放。

## 图形与文本对象接口

Display 与 Message 是硬件对象。文本输出由 Message 管理并自动刷新：

~~~mpl
AlertBoard.print("敌人数量：", enemyCount);
// 编译器在本次调用结尾自动输出 printflush(AlertBoard)
~~~

Display 提供接近 HTML5 Canvas 的基础绘制接口：

~~~mpl
MainScreen.clear(Color.black);
MainScreen.fill(Color.green);
MainScreen.fillRect(8, 8, 40, 20);
MainScreen.stroke(Color.white);
MainScreen.strokeRect(8, 8, 40, 20);
MainScreen.line(0, 0, MainScreen.width, MainScreen.height);
MainScreen.flush();
~~~

第一版只对目标 draw 指令提供一对一或接近一对一的封装；clear、fill、stroke、矩形、线和 flush 是优先范围。复杂路径、字体、图像、变换栈和保留式画布不在第一版承诺中。

## 资源独占与包

硬件声明的导出常量自动对项目 MPL/MIL 代码可见，不需要特别 import。包不能硬编码 link 编号、内存地址或组合屏幕布局；包通过 `import ... with {...}` 接收调用方传入的 Display、Message 等非内存硬件常量。包的内存预算从其自身 `.mplh` 自动汇总，不能由调用方手工传入。若同一可写硬件被多个模块写入，声明文件或构建配置应显式标注其共享/独占策略；编译器至少应给出冲突警告。
