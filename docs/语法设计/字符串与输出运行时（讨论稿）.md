# 字符串与输出运行时（讨论稿）

> 状态：v146 UTF-16 输出块、v159.7 `printchar` 专用输出、不可变 String 值、固定上界物理分配、运行时拼接/长度/相等、函数值复制和 `Message.print(...)` 自动刷新已实现；字符索引、切片和可变文本缓冲明确不属于第一版。

当前编译器已经实现完整的第一版纵切：String 字面量、两个字面量的编译期 `+` 折叠、动态拼接、`length`、`==`/`!=`、`val`/`var` 按值赋值、函数参数与返回值，以及 `Message.print(...)` 的 UTF-16 静态上界检查。`Message.print(...)` 内的 `String + String` 仍会被拆成顺序输出，不创建中间 String 值。所有动态序列与描述符表都由物理 Memory 自动承载，绝不回退为 mlog 的隐式对象/数值转换。

## 目标

MPL 的字符串以输出为中心。公开输出入口只有硬件对象的 `Message.print(...)`；不存在无目标的全局 `print(...)`。目标 mlog 的 print 缓冲区会顺序追加输出，因此：

~~~mpl
AlertBoard.print("状态：", state, "，血量：", health);
~~~

不需要构造中间字符串，编译器可直接按参数顺序生成输出，并在该调用结尾自动执行 `printflush(AlertBoard)`。

同样地，输出位置的 String 拼接会保持左到右顺序展开：

~~~mpl
val title: String = "MPL";
AlertBoard.print("运行 ", title + " v" + "1");
~~~

这会生成 `print "运行 "`、`print title`、`print " v1"` 和一次自动 `printflush`；它不是把 `title + " v1"` 赋给一个目标层 String 变量。

## v146 全局代码单元输出表（已确认）

编译器收集整个编译单元中用到的 UTF-16 代码单元。每个代码单元只生成一个输出处理块：

~~~text
代码单元“你” → 输出“你”的代码地址
代码单元“好” → 输出“好”的代码地址
代码单元“！” → 输出“！”的代码地址
~~~

字符串表不保存字符文本，而是保存这些输出处理块的地址序列：

~~~text
"你好！" → [地址(你), 地址(好), 地址(！)]
"你好"   → [地址(你), 地址(好)]
~~~

输出分发器逐项读取地址，通过宏中间语言的间接跳转进入代码单元输出块；处理块输出后回到分发器。输出块全局唯一，因此相同代码单元不会重复生成代码。

“代码单元”而不是“Unicode 字符”是有意的：v146 的 Message 文本缓冲使用 Java `StringBuilder`，400 的上限也按 UTF-16 长度计算。一个非 BMP 字符可能占两个代码单元，运行时必须保证两个单元在同一次缓冲拼接中按顺序输出。

v159.7 profile 使用等价但更短的表示：物理序列保存 `0..65535` 的代码单元数值，动态输出直接执行 `printchar`，不生成字符输出块、返回槽或间接跳转。高低代理项仍分别占一个物理槽，并按顺序追加到同一个 Java 文本缓冲，因此 `length`、拼接、比较与 v146 完全一致。

## 拼接、容量与值语义（已确认）

字符串的底层操作可以视为地址数组操作：

~~~mpl
var message: String = prefix + ", " + name;
AlertBoard.print(message);
~~~

常量拼接在编译期折叠。直接作为 print 参数的拼接也可拆成连续输出，避免创建中间字符串表。

若拼接结果要存入变量、传给函数或再次参与运算，运行时需要表达新的地址序列。输出块仍然复用；但 mlog 不能按运行时下标读取处理器变量，因此地址序列不能用“很多虚拟变量”实现。它必须放在编译器管理的物理 Memory 中：

~~~text
String 描述符表[handle] = {全局物理起始地址, 长度}
编译期布局[handle] = {容量, 所属物理分段}
物理地址 i = 对应代码单元输出块的 mlog 地址
分发器：read 地址 → set @counter 地址 → 输出块 → 返回分发器
~~~

分发器的当前索引、结束地址和返回地址是跨 tick 私有状态；一次动态输出不能重入。这些处理器变量槽由链接器自动分配和计量，不要求用户声明虚拟内存预算。

第一版固定采用**连续、不可变的代码单元地址序列**。每个变量、String 实参求值点、函数参数、函数返回槽、String 函数调用点、静态聚合元素和固定对象 String 字段拥有编译器分配的目标缓冲。String 实参会在从左到右求值时立即复制到调用点快照，因此后续实参即使调用函数并修改原 `var String`，也不会改变已经求出的实参；函数返回再复制到调用点结果缓冲，避免同一函数的后一次调用覆盖前一次结果。`+` 产生一个新序列，编译器可在结果直接传入 `Message.print(...)` 时消除该序列并输出两侧参数。不存在 String 的就地修改、用户分配器或显式释放。

每个 String 表达式都带有编译器推导的最大 UTF-16 代码单元长度；字面量长度精确已知，拼接长度为两侧上界之和，条件路径取已观察到的保守最大值。在优化后 HIR 上，独立的全程序容量分析器沿无递归调用图反复传播所有实参上界。函数 String 参数与返回槽使用全部调用点的安全最大值，每个调用结果缓冲使用被调函数的返回上界；从未调用的函数仍保守使用 target 最大容量。

`var String` 的物理缓冲不再一律预留 400 槽；分析器汇总初始值、所有分支、循环和函数中对该变量的赋值上界。实参快照同样采用传播后上界。循环内依赖旧值的自增长赋值仍无法证明有限上界，会在编译期拒绝。固定对象 String 字段等尚未建立值关系的不透明存储仍使用 target 上界；后续活跃区间分析还可以在不同生命期之间复用同一物理区间。缺少物理 Memory 或单个值超出 `400` 时均为构建错误。

因此，“输出块不会无限分配”与“运行时拼接结果需要序列空间”是两个独立问题：前者由全局去重解决，后者占用有静态上界且可回收的物理容量。String 支持 `length: Int`、`==` 与 `!=`；相等按 UTF-16 代码单元序列比较。第一版不支持字符索引、切片、正则、可变修改或任意容量的 StringBuilder。

## 当前边界

- MPL 源码不使用 @；v146 字符串表的地址读取和 `@counter` 间接跳转只发生在宏中间语言及其展开结果中，v159.7 专用后端改用 `printchar`。
- 普通数值、Bool 和 profile 明确支持的游戏对象可直接作为 `Message.print(...)` 参数输出，不需要先转换为 String。v146 profile 必须为每种非 String 参数提供保守的 UTF-16 长度上界，以便同样参加 400 上限检查。
- `Message.print(...)` 自动 flush，但不是原子事务；展开的 `print`、动态分发和 `printflush` 之间可跨 tick。
- 单次 Message 可见输出最多为 400 个 UTF-16 代码单元。每次 `Message.print(...)` 的静态最大长度必须不超过该值；没有隐式截断，也不在第一版提供 `printTruncated`。
- v159.7 的 `printchar` 动态代码单元输出已实现；它不改变 MPL 的 String 长度上限、值语义或拼接顺序，并在构建报告中记录相对 v146-style baseline 节省的指令与标签。
- mlog 产物使用 UTF-8，无法安全携带孤立代理项。编译器拒绝未配对代理项；合法的非 BMP 代码点在 v146 中由高代理槽输出完整代码点、低代理槽使用共享空操作块，在 v159.7 中由两个数值代码单元依次 `printchar`。两者的可见文本与 UTF-16 `length` 一致。
