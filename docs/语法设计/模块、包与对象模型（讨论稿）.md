# 模块、包与对象模型（讨论稿）

> 状态：包管理、import/export、包级 `.mplh`、硬件依赖注入、访问控制与无继承 OOP 已确认方向；清单文件的精确格式、对象池容量与析构语义待冻结。

## 模块与包

MPL 使用类似 TypeScript 的构建期包管理。依赖在构建时解析并统一链接到一个目标程序，不存在游戏内动态加载。

~~~mpl
import { Dashboard } from "@mpl/dashboard" with {
    screen: MainScreen
};
import { distance } from "./geometry";
~~~

项目硬件声明文件导出的 Display、Message 等特殊常量对项目代码全局可见，不需要从 @hardware 导入。`with {...}` 只用于向外部包注入这些非内存硬件常量。包的源码不知道调用方地图中的实际链接编号和布局。

包管理需要 manifest、锁文件、版本约束和目标 Mindustry 版本约束；所有依赖的物理/虚拟存储、字符串 runtime、标签、内部运行时槽和硬件需求由全局链接器统一分配。flag 不是可分配资源，MPL/MIL 均不能通过包声明取得它。

### 解析与锁定（建议冻结）

MPL 的包在构建期被链接进单份 mlog 或同一个多处理器部署包，不存在游戏内动态加载或包隔离。因此解析规则比 TypeScript/npm 更严格：

1. 相对路径 import 只解析项目/包内的规范化源文件；不得越出包根目录。
2. `workspace:` 依赖解析为工作区内的包；普通 `^1.2.0` 等语义化版本范围由已配置 registry 解析。
3. 每个外部包名在一个链接单元中只能有**一个精确版本**。若两个依赖要求无法共同满足的版本，构建失败，而不是把两套全局变量和 runtime 链接进同一处理器。
4. 首次安装/显式 `mpl install` 写入 `mpl.lock`；`mpl check` 和 `mpl build` 只使用锁定版本与完整性摘要，不在构建时悄悄联网改依赖。
5. 依赖图不允许循环。循环类型依赖、初始化顺序和静态函数 ABI 都会在单一 mlog 中变得不可判定，第一版直接给出循环链诊断。

建议项目 `mpl.json` 的最小稳定字段为：

~~~json
{
  "schemaVersion": 1,
  "name": "@example/alpha-monitor",
  "version": "0.1.0",
  "target": { "mindustry": "v146" },
  "entry": "src/main.mpl",
  "hardware": "src/hardware.mplh",
  "dependencies": {
    "@mpl/status-panel": "^0.1.0"
  }
}
~~~

包 manifest 还可用 `requires.mindustry.min` 和 `requires.capabilities` 声明最低 profile 能力。根项目 target 必须满足每个包的最低版本、能力和普通/World 处理器权限；不能仅因包源码没有直接出现新指令就假定兼容。

编译器为私有 Unit flag tag 生成的稳定 namespace 写入 `mpl.lock` 或部署元数据，不出现在用户的 `mpl.json` 中。`mpl.lock` 至少锁定 lock 版本、包名、精确版本、来源、内容 SHA-256、递归依赖和 package `.mplh` 的资源接口摘要。工作区包也记录内容摘要，避免“路径没变但硬件/内存要求已变”的不可复现构建。

用户不能定义宏。宏中间语言只允许调用编译器和标准库提供的基础游戏宏，这保证了包的资源声明、诊断与展开结果可审计。

每个外部包必须拥有自己的 `.mplh`。包的 `.mplh` 不绑定 `link` 编号，而是显式声明最小硬件需求：

~~~mplh
// @mpl/dashboard/hardware.mplh
require memory virtual(
    minSize: 512,
    mode: Pool
);

require screen: Display(
    minWidth: 176,
    minHeight: 176
);
~~~

内存需求由编译器自动传入并与项目 `.mplh` 声明的总预算统一核算，不出现在 `with {...}`。调用处只匹配命名的非内存资源：

~~~mpl
import { Dashboard } from "@mpl/dashboard" with {
    screen: MainScreen
};
~~~

编译器检查传入 Display 的编译期 width/height 等参数，并将包的物理/虚拟内存需求、对象池、字符串 runtime 一并纳入全局布局；任一预算或硬件约束不满足时直接报编译错误。`with` 只能传入 `.mplh` 导出的非内存硬件常量，键必须匹配包 `.mplh` 的命名需求；包源码中只读的 `screen` 绑定来自 `with {...}`，但不存在 `storage`、`Memory` 或内存下标 API。

## export 与访问控制

模块默认私有。对外可用的类、函数、常量和类型必须显式 export：

~~~mpl
export class Dashboard {
    private screen: Display;

    public fun render(): Void {
        this.screen.clear(Color.black);
        this.screen.flush();
    }
}

export fun normalize(value: Float): Float {
    return clamp(value, 0, 1);
}
~~~

第一版只需要 public 与 private。由于暂不支持继承，protected 没有必要。

## 简单对象模型

MPL 支持 class、字段、构造、this、实例方法与 new，不支持继承、虚方法、反射或自动垃圾回收：

~~~mpl
export class Counter {
    private value: Int;

    public fun Counter(initial: Int) {
        this.value = initial;
    }

    public fun add(amount: Int): Int {
        this.value += amount;
        return this.value;
    }
}

var counter = new Counter(0);
counter.add(3);
~~~

方法在目标层降级为以 this 为第一个隐藏参数的普通函数。字段的物理/虚拟布局由编译器统一分配；对象没有独立虚拟机，也不能指定或读取内存槽位。

## C++ 风格生命周期

new 表示显式对象分配，后续将引入与之配套的 delete 或等价的显式释放语义；不依赖垃圾回收。

由于 MPL 不提供运行时失败，`new` 的最大并发存活数量必须在编译期可证明。第一版应拒绝无法证明上界的动态分配，例如无限循环中未释放的 `new`。编译器基于该上界分配固定对象池；动态对象字段必须使用物理 Memory 的内部数值槽，而不是把一组处理器变量伪装成可运行时索引的数组。

自动局部对象可采用栈式生命周期；跨函数、跨 tick 保存的对象必须来自显式 `new`。for 中的 `Unit<T>` 初始为临时借用，但 `UnitSet.get(...)` 或逃逸提升可产生长期 Unit 句柄；第一版允许它作为变量与函数值，类字段支持待受限引用表实现后开放。第一版尚不提供用户自定义的每单位持久字段；编译器内部可为 Unit runtime 保留 ID/恢复元数据，但不会暴露成对象字段。物理 Memory 只能存数值，故动态对象第一版不得拥有任意 Unit、Building、Display、Message 等游戏对象引用字段；这类引用只能是静态槽或由未来受限引用表承载。

处理器代码重载会重置虚拟槽，物理内存布局变化也可能触发 runtime 重置。因此 `new` 的对象数据不默认跨重新部署持久化；持久化策略必须由未来的版本化存档 API 显式设计，不能由对象池暗中保证。
