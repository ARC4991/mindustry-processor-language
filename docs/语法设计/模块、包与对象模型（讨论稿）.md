# 模块、包与对象模型（讨论稿）

> 状态：项目内与 `workspace:` 包的 MPL/MIL 混合模块图、确定性 `mpl.lock`、单版本/循环/摘要/target 校验、`require`/`with` 注入、组合 Display 匹配，以及 public/private、class、顶层静态 new 和非逃逸局部分配点复用已实现。registry 传输、允许引用逃逸的动态对象池与跨分配点活跃区间复用仍待实现。

## 模块与包

MPL 使用类似 TypeScript 的构建期包管理。依赖在构建时解析并统一链接到一个目标程序，不存在游戏内动态加载。

~~~mpl
import { Dashboard } from "@mpl/dashboard" with {
    screen: MainScreen
};
import { distance } from "./geometry";
~~~

项目硬件声明文件导出的 Display、Message 等特殊常量对项目代码全局可见，不需要从 @hardware 导入。`with {...}` 只用于向外部包注入这些非内存硬件常量。包的源码不知道调用方地图中的实际链接编号和布局。

当前项目内模块实现遵守以下规则：

1. 所有 import 必须写在函数、变量和可执行顶层语句之前；
2. 相对路径可显式写 `.mpl` / `.mil`，也可省略扩展名；省略后同时命中两种文件或 `index` 文件时是歧义错误；
3. `export class`、`export fun` 和不可变的 `export val` 可导入，`export var` 被拒绝；
4. 每个可达模块只初始化一次，依赖模块按拓扑顺序先于入口执行；
5. 模块循环、越出 `src`、缺失文件、缺失 export、重复绑定和与全局硬件常量重名均在链接期报错；
6. 非入口模块的私有与导出顶层符号获得确定性内部身份，两个模块可拥有同名私有变量；函数参数、lambda 和块级局部变量仍按词法作用域遮蔽。

外部 `@scope/package` import 必须出现在当前模块所属 manifest 的直接依赖中，并由有效 `mpl.lock` 锁定；构建不会联网猜测版本。`with {...}` 的键必须与包 `.mplh` 的 `require` 完全一致，值必须是调用模块可见的硬件常量，类型和访问能力不匹配会直接失败。相对 import 不允许 `with`。

包管理需要 manifest、锁文件、版本约束和目标 Mindustry 版本约束；所有依赖的物理/虚拟存储、字符串 runtime、标签、内部运行时槽和硬件需求由全局链接器统一分配。flag 不是可分配资源，MPL/MIL 均不能通过包声明取得它。

### 解析与锁定（已确认）

MPL 的包在构建期被链接进单份 mlog 或同一个多处理器部署包，不存在游戏内动态加载或包隔离。因此解析规则比 TypeScript/npm 更严格：

1. 相对路径 import 只解析项目/包内的规范化源文件；不得越出包根目录。
2. `workspace:` 依赖已解析为工作区内的包；普通 `^1.2.0` 等 registry 版本范围尚未实现并会明确报错。
3. 每个外部包名在一个链接单元中只能有**一个精确版本**。若两个依赖要求无法共同满足的版本，构建失败，而不是把两套全局变量和 runtime 链接进同一处理器。
4. 首次安装/显式 `mpl install` 写入 `mpl.lock`；`mpl check` 和 `mpl build` 只使用锁定版本与完整性摘要，不在构建时悄悄联网改依赖。
5. 依赖图不允许循环。循环类型依赖、初始化顺序和静态函数 ABI 都会在单一 mlog 中变得不可判定，第一版直接给出循环链诊断。

项目 `mpl.json` 的最小稳定字段为：

~~~json
{
  "schemaVersion": 1,
  "name": "@example/alpha-monitor",
  "version": "0.1.0",
  "target": { "mindustry": "v146" },
  "entry": "src/main.mpl",
  "hardware": "src/hardware.mplh",
  "dependencies": {
    "@mpl/status-panel": "^0.1.0"
  }
}
~~~

包 manifest 还可用 `requires.mindustry.min` 和 `requires.capabilities` 声明最低 profile 能力。根项目 target 必须满足每个包的最低版本、能力和普通/World 处理器权限；不能仅因包源码没有直接出现新指令就假定兼容。包声明的是**最低** profile，而不是唯一 profile：同一包可在 v146 与 v159.7 构建，只要选定 target 满足其最低要求；profile 专属优化不得改变公开行为。

编译器为私有 Unit flag tag 生成的稳定 namespace 写入 `mpl.lock` 或部署元数据，不出现在用户的 `mpl.json` 中。`mpl.lock` 至少锁定 lock 版本、包名、精确版本、来源、内容 SHA-256、递归依赖和 package `.mplh` 的资源接口摘要。工作区包也记录内容摘要，避免“路径没变但硬件/内存要求已变”的不可复现构建。`mpl install` 是唯一会解析 registry 并更新锁文件的命令；`mpl check` 与 `mpl build` 发现锁文件缺失、摘要不符或未锁定依赖时直接失败。registry 的 URL、认证和缓存目录属于 CLI 配置，不进入源代码与锁文件语义。

用户不能定义宏。宏中间语言只允许调用编译器和标准库提供的基础游戏宏，这保证了包的资源声明、诊断与展开结果可审计。

每个外部包必须拥有自己的 `.mplh`。包的 `.mplh` 不绑定 `link` 编号，而是显式声明最小硬件需求：

~~~mplh
// @mpl/dashboard/hardware.mplh
require screen: Display(
    access: write
);

require screen: Display(
    minWidth: 176,
    minHeight: 176
);
~~~

处理器、Memory、对象池与 String runtime 完全由编译器在链接全部包后统一规划；包不得声明、预留或读取任何 Memory 预算。调用处只匹配命名的外部资源：

~~~mpl
import { Dashboard } from "@mpl/dashboard" with {
    screen: MainScreen
};
~~~

编译器严格检查传入 Display 的编译期 width/height、访问权限、数量和坐标映射；任一约束不满足时直接报编译错误。比较的是**规范化后的逻辑硬件描述**而非单个游戏方块实体：例如 `minWidth: 512, minHeight: 512` 可由 v146 的 3×3 个 176×176 大屏组成 528×528 逻辑屏来满足。未来 profile 若登记 128×128 物理屏，则 4×4 组合也可满足同一需求；硬件规格不能脱离 profile 凭空声明。`with` 只能传入 `.mplh` 导出的外部硬件常量，键必须匹配包 `.mplh` 的命名需求；包源码中只读的 `screen` 绑定来自 `with {...}`，但不存在 `storage`、`Memory` 或内存下标 API。

当前实现已严格验证名称集合、类型、`read`/`write`/`readWrite` 能力、`count: 1` 与 Display 最小尺寸，并支持包把已注入硬件继续转发给传递依赖。同一包在一个链接单元中是单例，多处 import 的 `with` 映射必须完全一致。组合布局不足或直接 Display 未声明尺寸时以 `MPL1416` 拒绝。

## export 与访问控制

模块默认私有。对外可用的类、函数、常量和类型必须显式 export：

~~~mpl
export class Dashboard {
    private screen: Display;

    public fun render(): Void {
        this.screen.clear(Color.black);
    }
}

export fun normalize(value: Float): Float {
    return clamp(value, 0, 1);
}
~~~

第一版只需要 public 与 private。由于暂不支持继承，protected 没有必要。

## 简单对象模型（已确认）

MPL 支持 class、字段、构造、this、实例方法与 new，不支持继承、虚方法、反射或自动垃圾回收：

~~~mpl
export class Counter {
    private value: Int;

    public fun Counter(initial: Int) {
        this.value = initial;
    }

    public fun add(amount: Int): Int {
        this.value += amount;
        return this.value;
    }
}

var counter = new Counter(0);
counter.add(3);
~~~

方法在目标层降级为以 this 为第一个隐藏参数的普通函数。构造函数与类同名；当前所有字段都必须在每条返回路径和构造器结尾完成初始化，读取尚未初始化的字段也是编译错误。`new Counter(0)` 总是得到非空 `Counter`；显式声明的 `Counter?` 可接收它或 `null`，并在 `!= null` 后获得非空收窄。

当前可编译字段为 `Int`、`Float`、`Bool`、静态 `String` 以及由这些标量组成的单层元组。每个可证明的 `new` 分配点获得唯一正整数私有句柄，字段按分配点落入互相隔离的编译器虚拟槽；元组字段逐元素布局。第一版不允许类字段保存另一个用户对象、`Unit`、`Building`、硬件引用或容器，这避免无界引用图和无法证明的跨 tick 所有权。对象之间仅能用 `===` / `!==` 比较身份；`== null` / `!= null` 只承担可空判断，两个对象之间的 `==` / `!=` 会被拒绝。

## 显式构造、编译器管理的生命周期（已确认）

`new` 表示显式构造和对象身份分配，但 Memory 与释放策略不暴露给源码。顶层变量初始化仍是长期存活的静态对象，并允许构造参数中有限嵌套的 `new`。函数、循环或块内还允许以下可证明不逃逸的局部形式：

~~~mpl
while (condition) {
    val temporary = new Counter(1);
    temporary.add(2);
}
~~~

局部 `new` 必须直接初始化 `val`。该引用只能读写字段、用 `===` / `!==` 比较身份，或调用经编译器证明不会泄露接收者的方法；不能返回、复制给另一个变量、作为普通实参传出、存入聚合或对象字段。构造器同样不能泄露 `this`。第一版效果分析对 `this.otherMethod()` 保守判为可能泄露，后续可用传递方法效果摘要放宽。违反任一约束都会在编译期报告 `MPL3708`。

每个非逃逸局部 `new` 仍只有一个分配点句柄和一组固定字段槽；控制流每次执行该声明都会重新调用构造器并覆盖这些槽，因此循环不会持续分配，也不存在运行时耗尽。递归已被禁止，同一个分配点不会重入。这一能力不是通用对象池：需要逃逸的动态对象仍须等待最大同时存活数证明、物理 Memory 字段布局、空闲槽回收与容量诊断。

MIL 保留 class、字段、构造器、实例方法、this 与 new；只有 Unit/Building/I/O 等游戏糖展开为 profile 宏。构建产生的 `.mil` 可由独立 MIL 前端重新解析和编译，而不是仅供阅读。

跨函数、跨 tick 保存的用户对象必须来自显式 `new`。for 中的 `Unit<T>` 是临时借用；普通 `Set<Unit<T>>.get(...)` 已可产生保存于当前处理器变量的 UnitRef，并在判空后跨 tick 重绑。当前 UnitRef 不能作为函数参数/返回值、用户类字段或跨 shard 值，循环变量逃逸提升也尚未实现。第一版尚不提供用户自定义的每单位持久字段；编译器内部可为 Unit runtime 保留引用和恢复元数据，但不会暴露成对象字段。物理 Memory 只能存数值，故动态对象不得拥有任意 Unit、Building、Display 或 Message 等动态游戏对象引用字段；固定硬件字段只允许由 `.mplh`/`with` 注入，不能由运行时值赋值。

处理器代码重载会重置虚拟槽，物理内存布局变化也可能触发 runtime 重置。因此 `new` 的对象数据不默认跨重新部署持久化；持久化策略必须由未来的版本化存档 API 显式设计，不能由对象池暗中保证。

## 明确留到后续版本

1. 泛型、接口、闭包和继承；
2. 用户对象作为字段、容器元素或跨 shard 消息的受限引用表；
3. 需要外部资源释放时的显式 `close` 协议；
4. 对象跨重新部署的版本化持久化。
