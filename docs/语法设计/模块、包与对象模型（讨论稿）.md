> 状态：包管理、import/export、硬件依赖注入、访问控制与无继承 OOP 已确认方向；清单文件的精确格式、对象池容量与析构语义待冻结。

## 模块与包

MPL 使用类似 TypeScript 的构建期包管理。依赖在构建时解析并统一链接到一个目标程序，不存在游戏内动态加载。

~~~mpl
import { Dashboard } from "@mpl/dashboard" with {
    screen: MainScreen,
    storage: Data
};
import { distance } from "./geometry";
~~~

硬件声明文件导出的特殊常量对项目代码全局可见，不需要从 @hardware 导入。with {...} 只用于向外部包注入硬件常量。包的源码只声明自己所需的 Display、Message、Memory 等类型，不知道调用方地图中的实际链接编号和布局。

包管理需要 manifest、锁文件、版本约束和目标 Mindustry 版本约束；所有依赖的虚拟内存、字符串表、标签、私有 flag 区间与硬件需求由全局链接器统一分配。

用户不能定义宏。宏中间语言只允许调用编译器和标准库提供的基础游戏宏，这保证了包的资源声明、诊断与展开结果可审计。

外部包应显式声明最小硬件需求：

~~~mpl
export requires {
    storage: Memory { minSize: 512, mode: Pool };
    screen: Display { minWidth: 176, minHeight: 176 };
}
~~~

调用处的 with {...} 是一次编译期匹配。编译器检查传入 Memory 的 size 与管理模式、Display 的编译期 width/height，以及其他基础参数；不满足需求时直接报编译错误。

`requires` 中的字段同时定义包源码内可见的只读资源绑定：上例的包实现可以直接使用 `storage` 和 `screen`，但不能重新赋值、重新绑定或假定它们对应任何 `link` 编号。调用方必须为每个必填字段提供一个硬件声明常量；普通局部变量、未声明的 Memory 和不满足最小参数的资源都不能传入。

## export 与访问控制

模块默认私有。对外可用的类、函数、常量和类型必须显式 export：

~~~mpl
export class Dashboard {
    private screen: Display;

    public fun render(): Void {
        this.screen.clear(Color.black);
        this.screen.flush();
    }
}

export fun normalize(value: Float): Float {
    return clamp(value, 0, 1);
}
~~~

第一版只需要 public 与 private。由于暂不支持继承，protected 没有必要。

## 简单对象模型

MPL 支持 class、字段、构造、this、实例方法与 new，不支持继承、虚方法、反射或自动垃圾回收：

~~~mpl
export class Counter {
    private value: Int;

    public fun Counter(initial: Int) {
        this.value = initial;
    }

    public fun add(amount: Int): Int {
        this.value += amount;
        return this.value;
    }
}

var counter = new Counter(0);
counter.add(3);
~~~

方法在目标层降级为以 this 为第一个隐藏参数的普通函数。字段存入编译器分配的虚拟内存或物理内存；对象没有独立虚拟机。

## C++ 风格生命周期

new 表示显式对象分配，后续将引入与之配套的 delete 或等价的显式释放语义；不依赖垃圾回收。

由于 MPL 不提供运行时失败，new 的最大并发存活数量必须在编译期可证明。第一版应拒绝无法证明上界的动态分配，例如无限循环中未释放的 new。编译器基于该上界分配固定对象池或虚拟内存槽位。

自动局部对象可采用栈式生命周期；跨函数、跨 tick 保存的对象必须来自显式 new。借用 Unit 不能作为类字段保存，后续的 ManagedUnit 才可作为字段。
