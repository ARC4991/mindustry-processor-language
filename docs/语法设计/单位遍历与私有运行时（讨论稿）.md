# 单位与建筑遍历、私有运行时（讨论稿）

> 状态：公开语法冻结为 `Unit.getAll类型()`、`.where(...)`、`.take(n)` 与循环内 Unit 对象操作。flag、`ubind`、单位 ID 与恢复是编译器 runtime 的私有实现；v146 lowering 仍须做游戏内原型验证。

> 当前编译器纵切：已实现直接写在 `for` 中的 `Unit.getAllDagger()` / `Unit.getAllAlpha()`、链式 `.where(...)`、稳定受控子集 `.take(n)`、标量字段读取与 `unit.move(x, y)`。`UnitSet` 保存、`size`、`get(index)`、长期 Unit 句柄、Building 遍历、嵌套循环与其它控制动作仍是本规范的后续实现项；它们不能被误认为已经可构建。

## 表面语法

MPL 以 Unit 与 Building 命名空间的类型遍历方法提供对象遍历：

~~~mpl
for (var unit : Unit.getAllAlpha()) {
    unit.move(100, 80);
    unit.mine(100, 80);
}

for (var turret : Building.getAllDuo(_.enabled)) {
    turret.shoot(targetX, targetY, true);
}
~~~

Unit.getAllAlpha() 与 Building.getAllDuo() 是编译器根据目标 Mindustry 版本内容表生成的 API。Alpha 与 Duo 分别编码在方法名中；它们不是用户可变变量，也不是字符串。

getAll类型() 返回惰性的、不可变的可迭代查询对象，而不是真实数组：

~~~mpl
val damaged = Unit.getAllAlpha().where(unit => unit.health < 50);

for (var unit : damaged) {
    unit.move(100, 80);
}
~~~

第一版 `UnitSet<T>` / `LinkedBuildingSet<T>` 可保存为 `val` 并重复使用；它们不是数组，也不自动构造快照。`where(...)` 是惰性过滤；读取 `size`、调用 `get(...)` 或进入 `for` 时才扫描游戏中的当前单位。

类型遍历可接受内联过滤 lambda：

~~~mpl
Unit.getAllAlpha(unit => unit.health < 50)
Unit.getAllAlpha(_.health < 50)
~~~

_ 是唯一参数的简写。过滤 lambda 只用于遍历，并在当前候选对象上内联执行。

过滤 lambda 是纯读取表达式：它只能读取当前对象的可感知属性并捕获常量或不可变标量；不能赋值、输出、绘制、调用控制方法、创建对象或启动另一轮 Unit 遍历。这样筛选不会悄悄认领或改变单位 AI。

`.where(...)` 可以任意串联；每一项都在前一项结果上继续收窄，语义是按书写顺序短路计算的逻辑 AND：

~~~mpl
val repairable = Unit.getAllAlpha()
    .where(_.health < 50.0)
    .where(_.ammo > 0.0);

// 等价于：
val same = Unit.getAllAlpha(_.health < 50.0 && _.ammo > 0.0);
~~~

### 稳定受控子集：`.take(n)`

普通 `for (var unit : Unit.getAllDagger())` 会按当前同队、可控制的 Dagger 全量遍历；循环体里有 `unit.move(...)` 时，就会对每一只匹配单位下达命令。需要固定编队大小时，在所有过滤条件之后写 `.take(n)`：

~~~mpl
for (var unit : Unit.getAllDagger()
    .where(_.alive)
    .take(3)) {
    unit.move(targetX, targetY);
}
~~~

`n` 必须是正 `Int` 字面量。`.take(n)` 不是随 `ubind` 游标变化的“本轮前 n 个”：编译器为该 `for` 私有认领至多 `n` 个符合前置 `where` 条件的单位，之后只有这些单位会进入循环体。已有成员优先保留；成员死亡、失去匹配条件、被其它控制者改写标记或首次没有足够候选时，下一轮再补充。这样地图上有更多 Dagger 时，`.take(3)` 也不会逐轮轮换并最终控制全部 Dagger。

第一版规定 `.take(n)` 必须位于全部 `.where(...)` 之后，且一个查询只能有一个 `.take(n)`。它目前只支持直接写在 `for` 的遍历目标上；保存 `UnitSet`、`size` 和 `get(index)` 的实现仍在后续纵切中。

### `where` 可读取的 Unit 字段（v146）

`where` 的字段是按 target profile 生成的白名单，而不是把 mlog 的任意 `sensor` 名称暴露给 MPL。以下是 v146 第一版稳定支持的只读字段；它们既可写在 lambda 中，也可从当前 `Unit<T>` 读取。

| MPL 字段 | 类型 | v146 来源与含义 |
| --- | --- | --- |
| `health`、`maxHealth`、`shield` | `Float` | 当前生命、最大生命与护盾 |
| `ammo`、`ammoCapacity` | `Float` | 弹药量与该单位类型的弹药容量；地图关闭单位弹药时，`ammo` 为容量 |
| `x`、`y` | `Float` | 逻辑坐标（tile 坐标，非像素坐标） |
| `rotation` | `Float` | 朝向角度，单位为度 |
| `range`、`speed`、`size`、`shootX`、`shootY` | `Float` | 攻击范围、速度、碰撞尺寸及瞄准坐标；均按游戏逻辑坐标表示 |
| `totalItems`、`itemCapacity`、`payloadCount`、`mineX`、`mineY` | `Int` | 携带物品数量、物品容量、payload 数量与采矿目标格坐标 |
| `alive`、`dead`、`shooting`、`boosting`、`mining` | `Bool` | 存活、死亡、开火、正在助推、正在采矿；`alive` 由底层 `@dead` 取反生成 |

例如：

~~~mpl
val movable = Unit.getAllDagger()
    .where(_.alive)
    .where(_.health > 50.0)
    .where(!_.mining);
~~~

`dead` 是与目标层一致的直接状态；业务代码通常优先写正向的 `alive`。`team`、`controlled`、`controller`、`type`、`name`、`firstItem`、`payloadType` 与 `color` 等 v146 可感知值，需先冻结相应的枚举、可空对象或打包颜色 API，第一版不能出现在 `where` 中。

`flag` 永远不属于白名单：它是 MPL runtime 的保留字段，MPL 与 MIL 都禁止读写。`id` 也不开放；v146 的 Unit 实体没有可供 mlog 读取的稳定 ID，不能把内容类型 ID 或缓存位置误当成单位身份。

> 命名更正：Mindustry v146 的单位内容名是 `dagger`，MPL 类型名是 `Dagger`，查询 API 是 `Unit.getAllDagger()`。`Dragger` 不是有效的 Mindustry 单位类型，编译器应报告未知类型。

## 已冻结的公开 Unit 模型

用户只需要认识两个类型：

| 类型 | 含义 |
| --- | --- |
| `UnitSet<T>` | 可筛选、可遍历、可计数并可按当前位置取出 Unit 的实时集合查询 |
| `Unit<T>` | 一个可长期保存的、不透明单位句柄；方法调用时编译器会重新绑定对应游戏单位 |

没有公开的 `UnitManager`、`ManagedUnit`、`UnitPool`、`manage()` 或 `service()` API。`.take(n)` 是普通集合上的声明式上限，不暴露 slot、flag、内存布局或管理器对象。

### UnitSet API

~~~mpl
val damaged: UnitSet<Alpha> = Unit.getAllAlpha().where(_.health < 50.0);

val count: Int = damaged.size;
val first: Unit<Alpha>? = damaged.get(0);

if (first != null) {
    first.move(100.0, 80.0);
}

for (var unit : damaged) {
    unit.move(100.0, 80.0);
}
~~~

| API | 类型 | 含义 |
| --- | --- | --- |
| `Unit.getAllAlpha()` | `UnitSet<Alpha>` | 当前可发现 Alpha 的实时集合查询 |
| `set.where(predicate)` | `UnitSet<Alpha>` | 在原查询上叠加只读筛选条件；可连续链式调用，条件以 AND 组合 |
| `set.take(n)` | `UnitSet<Alpha>` | 稳定私有认领至多 n 个符合前置过滤条件的单位；仅可作为当前阶段 `for` 目标的最后一个修饰器 |
| `set.size` | `Int` | 当前扫描结果的数量；读取时执行扫描，不是免费常量 |
| `set.get(index)` | `Unit<T>?` | 取出当前扫描中的第 index 个单位；越界返回 null |
| `for (var unit : set)` | `Unit<T>` | 依次取得集合中的单位对象 |

普通 `UnitSet` 没有稳定顺序，`get(0)` 只表示“本次扫描的第一个”，不能把 index 当作单位身份。`.take(n)` 保证的是由当前部署私有认领的成员集合，而不是它们的遍历顺序或不可变快照；游戏单位在其间生成、死亡或被接管时，下一次扫描仍可观察到变化。

### Unit 对象与生命周期

`Unit<T>` 可以保存到普通变量、作为函数返回值，未来也可作为受限对象字段；它代表同一只游戏单位，而不是当前的数组下标。`get(...)` 返回可空值，是因为查询可能没有足够多的单位。

~~~mpl
val leader = Unit.getAllAlpha().get(0);

if (leader != null) {
    while (leader.alive) {
        leader.move(100.0, 80.0);
    }
}
~~~

单位死亡、被装入 payload、被删除或不再可控制时，已有句柄不会抛出异常：`unit.alive` 变为 `false`，控制方法按目标层规则无效果。循环产生的 Unit 初始为临时句柄；若它被保存到循环外，编译器自动提升为长期句柄并计入隐藏 runtime 资源。无法在编译期证明长期同时存活句柄数量上界的程序会构建失败，规则与未来的 `new` 对象池一致，但用户无需手写容量。

控制方法是普通的副作用语句；如果游戏在该时刻拒绝控制（例如玩家接管或其他逻辑抢占），效果就是目标层命令未生效，不产生 MPL 运行时异常。若需要持续逻辑，用户显式书写 `while`；顶层 `for` 只执行一轮后按普通程序语义结束。

## LinkedBuildingSet 与 Building（已确认）

`Building.getAll类型()` 不是全地图查找。它只在当前 shard 的 `.mplh` 外部硬件契约中，枚举**已声明、已链接且 profile 类型匹配**的建筑；因此它没有 Unit 的 `ubind`、flag、AI 接管或私有认领 runtime。

~~~mpl
val turrets = Building.getAllDuo()
    .where(_.enabled)
    .where(_.health > 0.0);

for (var turret : turrets) {
    turret.shoot(targetX, targetY, true);
}

val first: Building<Duo>? = turrets.get(0);
~~~

`LinkedBuildingSet<T>` 与 `UnitSet<T>` 一样是惰性、弱一致、不可变查询，支持链式 `.where(...)`、`.size`、`.get(index)` 和 `for`。不过它的候选顺序是 `.mplh` 中的声明顺序而非游戏世界扫描顺序；`get(0)` 只在本次读取的仍有效链接中表示第一个候选，重连、拆除、队伍/权限变化后不承诺稳定身份。`Building<T>` 是不透明对象句柄，能保存、传参和通过 `building.alive` 判断，但不能转成数字、链接序号或 Memory 地址。

v146 第一版的只读公共字段为 `alive: Bool`、`health: Float`、`maxHealth: Float`、`x: Float`、`y: Float`、`enabled: Bool`、`size: Float` 与 `itemCapacity: Int`。`.where(...)` 只能读取这些 profile 白名单字段并捕获外层不可变标量，不能写硬件、I/O 或调用控制方法。后续 profile 可增加字段，但不得暴露 mlog 的任意 `sensor` 名称、内部 link 编号或对象/数值隐式转换。

控制方法同样由 profile 按建筑类型授权：例如可控制炮塔才有 `shoot(x: Float, y: Float, firing: Bool)`，支持启停的建筑才有 `setEnabled(enabled: Bool)`。调用方必须拥有 `.mplh` 声明的写权限，且该硬件只能有一个 shard 所有者；否则为构建期错误。动态地图拒绝控制时命令无效果，建筑失效时 `alive` 为 false，不产生 MPL 异常。Building 遍历不占用游戏的唯一 `@unit`，可与 Unit 遍历嵌套。

## 隐藏的 Unit runtime：bind、UnitRef 与 flag

`bind`、UnitRef、flag、单位 ID、扫描游标和任何物理/虚拟存储均不出现在 MPL 或 MIL 用户代码里。它们是编译器为了让上面的简单 Set/Unit API 可行而生成的私有 runtime。

v146 的 `ubind Alpha` 并非具有可依赖顺序的“随机数组访问”：它按处理器内部的类型游标轮转选择当前队伍中可逻辑控制的 Alpha。MPL 不承诺遍历顺序；用户只需把它理解为“依次给我一个可操作的 Alpha”。

当 `get(...)` 或被保存的循环变量需要长期 Unit 句柄时，runtime 将当前 UnitRef 保存到隐藏槽，并写入/验证隐藏 flag 标签。以后调用 `leader.move(...)` 时，编译器先用该隐藏引用重新 bind；代码重贴导致引用槽丢失时，再用 flag 扫描恢复。`size`、纯 `.where(...)` 与只读扫描不需要为每个单位建立长期句柄。

`.take(n)` 的私有认领以 v146 的 `ucontrol flag` 实现；写入该目标字段与 `ucontrol move` 一样会使被认领单位进入 LogicAI。编译器只对已认领或正在补充的候选单位写入它，绝不会扫描到一只就写一次。一个地图若还有手写 mlog、其它 MPL 部署或 RTS AI 同时控制同批单位，最后取得控制者为准。编译器不会向用户暴露 flag 让其手工修补。

私有 owner token 由游戏提供的 `@thisx`、`@thisy` 和 `@mapw` 计算，并为同一程序中的每个 `.take(n)` 位置保留不同子编号；因此通常不同位置的处理器不会互认单位。运行时把“token 相等且 `@controller === @this`”作为第二层所有权校验；补充候选还必须同时满足 flag 为 `0`、`@controlled == 0`。它仍是**合作式、弱一致**归属而不是锁：v146 没有单位实体 ID、原子 compare-and-set 或私有字段，手写 mlog 可以覆写任意 flag，RTS AI 也会使用 `0` / `1`。外部抢占后会在后续扫描收敛。若把处理器迁到新位置，旧标记无法被新位置自动识别，当前阶段应在原位置重新部署或等待后续的部署清理工具。

第一版不提供“用户自定义的每单位持久字段”。需要长期业务状态时，先用普通 MPL 对象/内存模型完成设计，再由编译器自动把它关联到隐藏单位 ID；届时仍不会要求用户改写为 UnitManager API。

## v146 遍历 lowering 与已知弱一致性

`Unit.getAllAlpha()` 只会遍历当前处理器队伍中、目标 profile 标为 `logicControllable` 的 Alpha；它不是全地图搜索，也不构造数组或快照。v146 为每种单位类型维护轮转绑定游标，而不是提供数量或实体 ID。普通遍历采用隐藏 UnitRef 哨兵：

~~~text
1. ubind Alpha；若为空则退出；保存首个单位为 sentinel。
2. 对当前单位执行纯过滤器；匹配时执行循环体。
3. 循环尾部重新绑定 sentinel；若不存在或 @dead 则安全结束本轮。
4. ubind Alpha；若为空或等于 sentinel 则结束；否则回到第 2 步。
~~~

循环体、`continue` 和 `break` 都通过 MIL 标签与 `@counter` 降级。循环变量的方法直接作用于当前绑定单位，无需按 ID 重查。单位在遍历期间生成、死亡、改变队伍或被其它处理器接管时，结果是弱一致的：可能漏掉、提前结束，绝不承诺快照或恰好一次。

`.take(n)` 额外生成两次上述扫描：第一遍只保留当前 owner token 且 `@controller === @this` 的匹配单位并释放失配或超额标签；第二遍只对这两个条件均满足的单位执行循环体，并从 flag 为 `0`、`@controlled == 0` 的匹配候选补齐空位。第二遍的 `ucontrol move` 前必有 owner 校验，因此它的循环体至多作用于 n 个当前认领单位。

第一版禁止**任何** Unit 迭代嵌套（包括在 `UnitSet` 循环体、过滤 lambda 或非纯函数内再次开启 Unit 遍历）。游戏只有一个 `@unit`，这一限制比仅禁止“同类型嵌套”更诚实。Building 迭代不改写 `@unit`，可与 Unit 循环组合；日后若引入隐藏引用的保存/重绑协议，再放宽该限制。

实现前必须用 v146 游戏内原型覆盖：零单位、单单位、多单位、哨兵死亡、单位生成/销毁、代码重贴和外部处理器抢占。验收标准是循环必定退出，且 runtime 不会把 flag 细节泄漏为 MPL 语义；测试结果只会影响扫描优化与诊断，不会改变本文已冻结的表面语法。

## 剩余实现任务

1. 为 `UnitSet` 保存、`size`、`get(...)`、break/continue 建立 AST/HIR/MIL lowering、标签预算和 golden mlog 测试；
2. 扩展私有 Unit runtime：长期句柄提升、部署清理、跨处理器冲突诊断与重新绑定逻辑；
3. 为 Unit 属性和控制方法生成直接的 mlog `sensor` / `ucontrol` 指令，并补齐 profile 能力诊断；
4. 在 `mpl init`、部署报告中记录 runtime namespace 和外部 mlog/RTS 控制冲突警告；
5. 在单处理器稳定后，再设计多 shard 下 Unit runtime 的唯一控制者与数值消息 ABI；公开 MPL API 保持不变。
